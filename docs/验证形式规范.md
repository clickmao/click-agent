# 验证形式规范（Verification Form Spec）

> 立档：R370（2026-09-13）。用户逐字令：「注意别忘验证形式，要加入规范内」。
> 性质：**强制规范**（与《千轮准则》同级）。机检入口：`src/agent.tests/VerificationFormTests.cs`。
> 一句话：**任何"已完成/已修复/已验证"的表述，必须能指到本规范的登记行与可复现证据命令；指不到 = 未验证。**

## 一、验证形式阶梯（L0–L4）

| 等级 | 含义 | 证据必须是什么 | 允许的表述 | 禁止的表述 |
|---|---|---|---|---|
| **L0** | 未验证（仅存在） | 无 | "已编写，未验证" | "已完成""可用" |
| **L1** | 静态检查 | 编译/语法/结构扫描的命令与输出 | "静态通过（编译/语法级）" | "已验证可运行""功能正常" |
| **L2** | 单测/组件行为断言 | 断言绑定**组件真实行为**（非"LLM 说 OK"） | "组件行为已验证（测试 N 通过）" | "端到端可用" |
| **L3** | 真机运行 | 真跑进程/产物/端到端的日志、产物路径、退出码 | "真机验证通过（附产物与日志）" | "生产就绪" |
| **L4** | 对抗/负向控制 | 注入缺陷必失败（负向控制）的对照实验结果 | "含负向控制的验证通过" | —— |

**等级判定不看代码"看起来对不对"，只看证据形式。** 静态检查无论多严密，最高只能申报 L1。

## 二、铁律（R1–R6）

- **R1 无登记 = 未验证。** 能力必须登记在 `docs/verification-registry.json`；未登记的能力，其任何"已完成"表述无效。
- **R2 证据可复现。** 每行须有 `evidence_cmd`（可直接复制执行的命令）+ `evidence_path`（产物/测试/文档路径，必须真实存在）。
  - **R2b `evidence_cmd` 必须真能执行（R411-V 增补）。** 命令里出现的仓库相对路径必须存在；确需引用「必须不存在」的路径（退役反证类命令）时，必须在该行 `cmd_expect_absent[]` 显式声明 —— 声明与事实矛盾（声明不存在却存在）同样报红。构建产物（`bin/`、`obj/`）不在此列：干净检出下本就不存在，其上游由 `covers[]` 的源码路径钉住。
  - **R2c `covers[]` 必须指向真实源码（R411-V 增补）。** 覆盖声称只能引用存在的文件（`路径(说明)` 形式先剥离括号内容）。史实：R408 退役引擎后，多行 `covers[]` 仍指向已删文件、`evidence_cmd` 仍调用已删二进制，而当时机检只验 `evidence_path` ⇒ 登记表「看着有事」实则不可执行（R411-V 一次抓出 9 行）。
  - **R2d 测试过滤器必须可解析（R411-V 增补）。** `--filter FullyQualifiedName~X` 的 `X` 必须在 `src/agent.tests` 的类名/方法名中确有匹配；指向已删测试的残留过滤器会让整行「看起来有证据」。
  - **R2e「证据 ↔ 器具」版本绑定（R473 增补）。** 产品面证据行必须有 `evidence_generated_with`：证据形态（`evidence_kind`）、是否对**证据字节**上闸（`pin_status` + `pin_reason`）、证据字节 `sha256[:12]`、生成器具路径及其 `sha256[:12]`、绑定强度（`binding`）、审计轮号（`audited_by_round`）。三条硬闸：①`frozen` 行的 `artifact_sha12` 必须等于证据文件**现盘字节**；②`instrument` 非空时 `instrument_sha12` 必须等于器具**现盘字节**（器具一改即判红 = 重审信号）；③`binding=self-attested` 只在产物自带 `provenance` 且逐字段一致时成立，产物已自证却登记成 `audit-pin` 同样判红。史实：Q24/Q25 定因的「r444 precheck 证据被控制臂静默覆盖」正是**证据换了主人而登记表不说话**。
  - **R2f 产品面证据必须有绑定（R473 增补）。** `evidence_path` 以 `eval/` 或 `docs/reports/` 开头且等级为 L1–L4 的行缺该字段即判红（`L0` 无证据可绑，不强制）。
- **R3 L≥2 必须有负向控制。** 声明"可运行/已修复"必须回答"怎么证明它坏的时候会红"；无 `negative_control` 不得申报 L2 以上。
- **R4 禁止静态冒充运行。** `py_compile`、`csc /t:module`、正则扫描、"仅阅读代码"等静态手段**最高只能 L1**；L≥2 必须真跑产物或进程。
- **R5 断言必须绑定真实行为。** 评测/测试的通过条件必须能指出被验证组件的可观测行为（隔离断言、真实读写、真实进程）。**只查"LLM 返回 true"这类空心判据，视为未验证**（史实：R149 用户定性"判定空心/数据幻觉"）。
- **R7 AOT 登记口径（用户钦定 2026-09-13）。** AOT 编译校验（NativeAOT 发布 / 0 IL 警告 / 发布体积）**只在发布 tag 时执行并登记**；非发布轮次的 AOT 结果只能作为参考证据，**不得**作为该轮任何能力的登记依据或等级判定。收口清单里不再把「AOT 发布」列为非发布轮的强制项。
- **R6 表述纪律。** 结论用词不得越过证据等级：L1 只能写"静态通过"；L2 只能写"组件行为已验证"；只有 L3/L4 才能写"真机/端到端已验证"。回退时须写明降级原因。

## 三、登记表

- 文件：`docs/verification-registry.json`（机读；schema `verification-registry/v1`）。
- 字段：`id` / `capability` / `level` / `evidence_cmd` / `evidence_path` / `negative_control` / `covers[]`（被验证的源文件路径，用于覆盖度机检） / `owner_round`。
- 覆盖度机检：`src/` 下每个 `IResponseSegmentPlugin` 实现文件必须在某行的 `covers[]` 中出现 —— **新增插件未登记，测试必红**。
- **退役能力的登记形态（R411-V 定式）**：能力随改造消失（源被删）时，登记行**不得保留原等级**，必须收口为：`level=L0`（不可复现）+ `evidence_cmd` 改为**可执行**的退役账断言（归档件存在 + 源已删，删掉的路径登进 `cmd_expect_absent[]`）+ `gap_note` 写明退役轮次、归档指针与「复现需重建什么」。史实：R408 退役本地引擎后，R389/R400/R402 三行仍挂 L4/L4/L3 与已删代码 ⇒ 等于对外宣称不存在的能力已通过运行级验证。
- **`evidence_generated_with` 语义与代价（R473）**：`frozen` = 证据字节被钉住（改一个字即判红）；`live` = 字节可变故不上闸（追加式台账/工作区未入库产物/目录聚合/派生件），原因入 `pin_reason`（词表：`archived-per-round` / `append-only-ledger` / `worktree-only` / `directory-aggregate` / `self-derived`）。`audit-pin` 是诚实的下限：它只说「审计在本轮按这些字节绑定过」，**不**宣称「证据由该器具版本生成」——后者只有产物自证（`self-attested`）才能宣称。
- **刻意的代价**：器具（`scripts/**`、`eval/**` 的 .py/.sh）被改动后，引用它的登记行会判红 —— 这是「证据必须跟着器具重审」的信号而非噪声。重审 = 确认证据仍成立后跑 `python3 eval/capability/bind_evidence.py --apply`（幂等；写前断言序列化器逐字节复现原文件，写后读回 + `git diff --numstat`），并把重审轮号写进 `audited_by_round`；**盲目 `--apply` 等于把「未重审」洗成绿**。
- 机检负向控制覆盖 7 类注入坏行（漏项/越级/静态冒充/未登记插件/cmd 路径/`covers` 路径/测试过滤器）+ 6 类绑定注入（冻结 pin 被改写 / 器具 sha 不符 / 产品面缺字段 / 伪自证 / 非法形态 / 器具无 sha）+ 正向控制（`cmd_expect_absent` 声明生效 ∧ 正确冻结 pin 不判红）；见 `Validator_CatchesInjectedDefects`。
- AOT 行（`aot.publish.zero_il`）带 `registration: release_tag_only`；登记表头 `aot_check_policy: release_tag_only` —— 见 R7。

## 四、与既有文档的关系

- 《千轮准则》（`docs/reports/iteration-master-plan.md` §0-0/§0-1）：本规范是其中"每轮记录修改点 + 性能"的**证据形式细则**。
- `DevPlanDocRefTests.cs`（开发计划 DocRef 防漂移）：本规范把同类"文档-代码锚定"思路扩展到**能力-证据锚定**。
- 本规范不替代 AOT/凭据卫生/零 shell 等工程铁律，而是规定它们**如何被证明**。

## 六、每轮收口清单（钩子）

1. 本轮新增/修改能力 → 是否已在 registry 增改行？
2. 每个 L≥2 行 → 负向控制是否真实存在且能跑？
3. 汇报中的"已验证"用词 → 是否与等级一致（R6）？
4. `VerificationFormTests` 是否全绿？
5. 非发布轮：是否**没有**把 AOT 发布写成本轮强制登记项（R7）？
6. 本轮若改了器具或证据 → 绑定是否已重审（`python3 eval/capability/bind_evidence.py --check` 绿，且 `audited_by_round` 已更新）？
