# 验证形式规范（Verification Form Spec）

> 立档：R370（2026-09-13）。用户逐字令：「注意别忘验证形式，要加入规范内」。
> 性质：**强制规范**（与《千轮准则》同级）。机检入口：`src/agent.tests/VerificationFormTests.cs`。
> 一句话：**任何"已完成/已修复/已验证"的表述，必须能指到本规范的登记行与可复现证据命令；指不到 = 未验证。**

## 一、验证形式阶梯（L0–L4）

| 等级 | 含义 | 证据必须是什么 | 允许的表述 | 禁止的表述 |
|---|---|---|---|---|
| **L0** | 未验证（仅存在） | 无 | "已编写，未验证" | "已完成""可用" |
| **L1** | 静态检查 | 编译/语法/结构扫描的命令与输出 | "静态通过（编译/语法级）" | "已验证可运行""功能正常" |
| **L2** | 单测/组件行为断言 | 断言绑定**组件真实行为**（非"LLM 说 OK"） | "组件行为已验证（测试 N 通过）" | "端到端可用" |
| **L3** | 真机运行 | 真跑进程/产物/端到端的日志、产物路径、退出码 | "真机验证通过（附产物与日志）" | "生产就绪" |
| **L4** | 对抗/负向控制 | 注入缺陷必失败（负向控制）的对照实验结果 | "含负向控制的验证通过" | —— |

**等级判定不看代码"看起来对不对"，只看证据形式。** 静态检查无论多严密，最高只能申报 L1。

## 二、铁律（R1–R6）

- **R1 无登记 = 未验证。** 能力必须登记在 `docs/verification-registry.json`；未登记的能力，其任何"已完成"表述无效。
- **R2 证据可复现。** 每行须有 `evidence_cmd`（可直接复制执行的命令）+ `evidence_path`（产物/测试/文档路径，必须真实存在）。
- **R3 L≥2 必须有负向控制。** 声明"可运行/已修复"必须回答"怎么证明它坏的时候会红"；无 `negative_control` 不得申报 L2 以上。
- **R4 禁止静态冒充运行。** `py_compile`、`csc /t:module`、正则扫描、"仅阅读代码"等静态手段**最高只能 L1**；L≥2 必须真跑产物或进程。
- **R5 断言必须绑定真实行为。** 评测/测试的通过条件必须能指出被验证组件的可观测行为（隔离断言、真实读写、真实进程）。**只查"LLM 返回 true"这类空心判据，视为未验证**（史实：R149 用户定性"判定空心/数据幻觉"）。
- **R6 表述纪律。** 结论用词不得越过证据等级：L1 只能写"静态通过"；L2 只能写"组件行为已验证"；只有 L3/L4 才能写"真机/端到端已验证"。回退时须写明降级原因。

## 三、登记表

- 文件：`docs/verification-registry.json`（机读；schema `verification-registry/v1`）。
- 字段：`id` / `capability` / `level` / `evidence_cmd` / `evidence_path` / `negative_control` / `covers[]`（被验证的源文件路径，用于覆盖度机检） / `owner_round`。
- 覆盖度机检：`src/` 下每个 `IResponseSegmentPlugin` 实现文件必须在某行的 `covers[]` 中出现 —— **新增插件未登记，测试必红**。

## 四、与既有文档的关系

- 《千轮准则》（`docs/reports/iteration-master-plan.md` §0-0/§0-1）：本规范是其中"每轮记录修改点 + 性能"的**证据形式细则**。
- `DevPlanDocRefTests.cs`（开发计划 DocRef 防漂移）：本规范把同类"文档-代码锚定"思路扩展到**能力-证据锚定**。
- 本规范不替代 AOT/凭据卫生/零 shell 等工程铁律，而是规定它们**如何被证明**。
