## 1. 口径纠正（先纠后判 —— 旧数字有杂质）

| 此前流传的口径 | 实际情况（证据） | 影响 |
|---|---|---|
| 「全量建索引 = **实测** 21.6 min」 | **是外推**：真跑 300 块 / 61.061 s / 203.54 ms/块；6375 = 300 块的线性放大（`/tmp/bge_bench.log` 原文 `extrapolate_full_repo_chunks=6375 est_minutes=21.6`） | 21.6 min 不是实测数字；数量级仍成立（单块 203.5 ms 是实测） |
| 「索引 **306 MB**」 | **306 MB 是进程 RSS（含 Q8 模型常驻），不是索引体积**；managed 93.6 MB。按 512 维实算索引本体：fp32 = 2.0 KB/块 → 6375 块 ≈ **12.4 MB**；int8 ≈ **3.1 MB** | 索引体积比流传值小 25~100 倍；「建不起」的主因是**时间**不是体积 |
| 「**不加探讨就全量**」 | 用户 R369 已推翻：**不要全量** | 本判定的对象改为「agent 关注范围」与「是否根本不需要」 |

> 本文所有表格：**实测**栏只放现场测量值；**外推/换算**栏按标注呈现。

## 2. 规模与「agent 关注面」（现场测量）

| 集合 | 定义 | 文件 | 字节 | 行 | 块数 @465 字符 |
|---|---|---|---|---|---|
| S1 | src+docs+samples+eval+scripts（全量） | 970 | 13,185,379 | 327,763 | 21,976 |
| S2 | `src/**/*.cs`（代码面） | 301 | 2,010,509 | 51,188 | 3,351 |
| S3 | `src` + `docs/**/*.md` | 388 | 3,124,641 | 64,850 | 6,720 |
| **S4** | **最近 30 次提交触及的文件**（关注面代理 A） | 104 | 1,451,164 | 27,731 | 2,419 |
| **S5** | **探索文档显式引用的 `src/*.cs`**（关注面代理 B） | 60 | 724,223 | 16,560 | 1,559 |

**读法**：真正被 agent 显式关注的代码面（S5）只有全量的 **5.5% 字节 / 7.1% 块**。即「只对 agent 关注范围建索引」在**规模上是成立的**——问题在于剩下的成本（§4）。

## 3. 检索基准：暴力全扫 vs 倒排索引（现场测量，301 个 `.cs` / 2.0 MB）

| 方式 | 构建成本 | 常驻 | 每查询延迟 | 语义 | 断点 |
|---|---|---|---|---|---|
| **冷扫（无缓存，逐次读盘）** | 0 | 0 | **7.35 ms** | 子串（含复合标识符片段） | — |
| **温扫（文件已驻留内存）** | 7.1 ms（载入全部） | ≈2 MB 文本 | **0.74 ms** | 同上 | — |
| token 倒排索引 | 314.6 ms | **4.06 MB**（8144 键） | 3.9 µs | **不等价**：漏 `AOT`/`ContextAssembler` 这类**复合标识符内的子串**（实测 3 个查询漏匹） | 48 次查询 |
| trigram 索引（补语义等价） | 3,156.7 ms | **45.27 MB**（86,217 键） | 1.375 ms | recall 完备 + 假阳性（需后验过滤） | 429 次查询 |

**读法**：
- 现有全扫的**延迟本身不是问题**（7 ms 级），索引能省的只有 ~7 ms/查询；换来的却是 4~45 MB 常驻 + 300 ms~3.2 s 构建 + **额外的语义正确性风险**（token 倒排会漏复合标识符，trigram 又要 45 MB）。
- 「10 万条内存查询 P95 < 10 ms」（exp1 §5 A5）在本项目规模下属于**没有对应痛点**的指标：2 MB 语料全扫就已经 7 ms。

## 4. bge 向量化成本（锚定实测：203.54 ms/块，4.91 块/s，RSS 306 MB 含模型）

| 集合 | 块数 | 建索引耗时（外推） | 索引体积 fp32 / int8 | 占全量块数 |
|---|---|---|---|---|
| S1 全量 | 21,976 | **74.5 min** | 42.9 MB / 10.7 MB | 344% |
| S3 src+docs | 6,720 | 22.8 min | 13.1 MB / 3.3 MB | 105% |
| S4 近 30 提交 | 2,419 | 8.2 min | 4.7 MB / 1.2 MB | 38% |
| **S5 关注面（最小）** | 1,559 | **5.29 min** | 3.0 MB / 0.8 MB | 24% |

**对照**：查询期 bge **已经在用**，中位 **462 ms/case**（§5），即"按需 embedding"通路已存在且成本可接受。

**读法**：即使把范围压到 agent 关注面（S5），预建也要 **5.29 min + ~300 MB RSS**；而"不预建、查询期按需算"的现状成本是 462 ms/case。→ **预建索引的收益无法覆盖成本**。

| 维度 | 值 | 对应 KPI |

## 6. 教训/失败签名重复度（exp5 的需求证据）

| 项 | 值 |
|---|---|
| 失败 | **64 / 4391 = 1.46%** |
| 不同失败签名 | **26** 种；其中 **≥3 次 = 7** 种 |
| 头部集中度 | top2 签名占全部失败 **49%**（`llm_calls 不足` 27 次、`reply 过短` 18 次） |
| 存量资产 | `data/executor-lessons.json` = 1 条；`data/guardrails.json` = 4 条；`data/roles/` **空**；`failureClusters.json` **不存在** |

**读法**：重复模式**存在但量小**（26 种签名 / 7 种 ≥3 次）→ **重量级教训表不成立，轻量（role 模块内、去重计数、≥3 前置注入）成立**，且恰好能把 top2（占近半失败）收敛成 2 条记录。

## 7. 判定表（阈值写死在探针里，可复算）

| 探索项 | 判定指标 | 阈值 | **判定** |
|---|---|---|---|
| **exp1a 关键词倒排索引** | 冷扫 7.35 ms / 温扫 0.74 ms / 建索引 315 ms / 4.06 MB / 断点 48 次 | 冷扫 <50 ms 且温扫 <5 ms → 延迟收益不足以抵消构建+内存+语义代价 | **不需要**（改为「惰性扫描 + 结果缓存」；仅在语料 >50 MB 文本或跨会话复用需求出现时重评） |
| **exp1b bge 预建索引** | 最小关注面 S5 = **5.29 min**；查询期 bge 已有 462 ms/case | 最小范围 <1 min 才考虑预建 | **不需要**（保留查询期按需 embedding，不做持久索引） |
| **exp2 多方案 menu 问询** | `gate_to_ask` 0.48%，clarify 29 次 | 现有评测**无交互场景** | **不可判**（需新埋点：见 §9） |
| **exp3 步骤对齐校验** | 长链 99.39% vs 短链 98.44% | 长链低于短链 5 pt 以上才建 | **不需要**（数据反向：长链更好） |
| **exp5 教训表** | 26 种签名 / 7 种 ≥3 次 / top2 占 49% | ≥3 次签名 ≥5 种 → 轻量值得做 | **需要（轻量）**：role 模块最小实现（提交 API 归 role，`data/roles/{roleId}.lessons.json`） |

**一句话总结**：**索引类能力（exp1a/exp1b）在本项目规模下「根本不需要」**；`agent 关注范围` 口径虽能把规模压到 5~7%，但最小口径的 bge 预建仍需 5.3 min，收益仍不成立 → 结论是**不预建**，检索走「惰性扫描 + 缓存 + 查询期按需 embedding」。**需要开发的只有 exp5 的轻量教训表**（且归属 role 模块）。

## 8. 诚实边界（不粉饰）

1. **评测非交互**：512 轮评测全部是单轮合成场景，**没有任何真实交互式提问** → exp2 的「0.48%」只能说明"评测里没测到"，**不能**说明"生产里不需要"。判定为**不可判**而非不需要。
2. **长任务是合成的**：`subtasks` 字段由框架切分产生，不等于人类级长任务 → exp3 的"数据反向"**不能**外推成"工业长任务不需要对齐校验"。
3. **21.6 min 是线性外推**（300 块 → 6375 块），未真跑全量；单机单线程 CPU（Q8）。
4. **token 换算常量 4.0 B/token 非分词器实测**，只用于量级比较；本判定未依赖它（关键结论都用延迟/块数/文件数）。
5. **trigram 索引为 superset**（recall 完备 + 假阳性），1.375 ms/查询 未含后验过滤成本。
6. 冷扫 7.35 ms 建立在 **2 MB 语料**上；用户仓库大一两个数量级会改变结论 → 见 §9。

## 9. 重评条件 / 新埋点定义（推翻本判定的触发条件）

| 项 | 触发重评的条件 | 需要补的埋点（KPI 定义） |
|---|---|---|
| exp1a | 文本语料 > 50 MB，或单会话代码检索 > 5000 次 | `search_queries_per_session`、`corpus_bytes`、`search_p95_ms` |
| exp1b | 语义召回成为回答准确性瓶颈（rel 中位跌破 0.5）或出现跨会话复用 | `semantic_recall_needed_count`、`bge_hit_rel` |
| exp2 | 交互式评测上线 / 真实会话中出现"多方案未定却继续执行" | `ambiguous_branch_count`、`ask_shown_count`、`ask_resolved_task_success_delta` |
| exp3 | 出现真实长任务（>10 步）失败样本 | `long_task_steps`、`step_mismatch_detected`、`long_task_fail_rate` |
| exp5 | 失败签名 ≥3 次的数量 ≥15，或 role 教训存量 ≥50 条 | `lesson_repeat_count`、`lesson_injected_precision` |
