## 2. 实测数据（本轮新增，探针 `/tmp/bge_bench`）

> 用户问「bge 自动建立效果如何？」—— 以下为**本机实测**，非估算。探针复用 `agent.embedcpu` 真实实现，语料 = 本仓 `src/**/*.cs` 切片（480 字符/块，近似 bge 512 上下文）。

| 指标 | 实测值 |
|---|---|
| 冷加载 | `cold_load_ms=0`（**惰性**：构造不加载，首次 Embed 才加载 — 与 §1.4 双检锁一致） |
| 样本 | 300 块，平均 465 字符（来自 296 个 `.cs` 文件） |
| 单块耗时 | **203.54 ms/块** |
| 吞吐 | **4.9 块/s ≈ 2 287 字符/s** |
| 内存 | managed 93.6 MB / **RSS 306.0 MB**（模型常驻） |
| **全仓外推** | 仓库源码+文档 3 061 209 B ≈ **6 375 块 → 约 21.6 分钟**（单线程、不含增量失效重算） |

**仓库规模事实**：`src/` 下 296 个 `.cs`（排除 bin/obj）、`docs/` 78 个 `.md`、`git ls-files` 989 个文件、源码+文档合计 3.06 MB。

**结论（数据说话）**：
- bge **全量**自动建索引 = **21.6 分钟 + 306 MB 常驻**，且任何一次文件变更都要重算受影响块 —— 这与用户钦定的「本质上不主动探索全量」**正面冲突**。
- 但 bge 的**增量/按需**使用成本可控：单块 203 ms ⇒ 对「已由关键词命中/正在页面显示的 20~50 个片段」做语义重排 ≈ 4~10 秒（后台异步可接受）。

## 3. 候选方案对比（直接回答 I4）

| | **方案 A：纯关键词倒排** | **方案 B：纯 bge 向量索引** | **方案 C：插件返回 graph** | **方案 D：混合分层（推荐）** |

**三个否决性判断（基于证据）**：
1. **B 不能做「全量自动建索引」**：21.6 min / 306 MB 与用户钦定前提冲突（§2）。B 只能作为**按需二级重排**。
2. **代码引用索引只能走 C（graph）**：bge 语义向量天然给不出「谁引用了谁」的结构化边；且引用索引的存储/遍历基础完全缺失（§1.6-1）。插件返回强类型边集可**直接复用**已有契约（单行 JSON [src/agent/registry/CapabilityPlugin.cs:37]）与外部脚本范式（task-json + JSON Lines 事件流 [src/agent.skills/ScriptPluginRunner.cs:95-178]）。

## 4. 推荐设计（分层，全部惰性）

### 4.1 数据模型（落盘，自建头 + 校验）

```
magic "AKIX" (4B) | version u16 | flags u16 | fileFingerprintCount u32 | payloadLen u32
payload = gzip( STJ source-gen JSON )   ← 键名短、字典化、可扩展 "x:" 前缀
```
- 先例：Role `.rbin` 16B 头 + `AES-GCM(gzip(JSON))` [docs/api.md:1409]。索引**不需要加密**（非凭据），但需要 **version + 校验**（防旧版本读坏、防截断）。
- 三个条目集：① 倒排 `token → docIds`；② 文件指纹 `path → {mtimeTicks, size, hash?}`；③ 引用边 `symbol → refs[]`（可选，来自插件）。

### 4.2 惰性加载 + 加载校验（用户逐字要求「需惰性加载」+「加载校验」）

- 照抄 `BgeCpuEmbedder.EnsureInitialized` 双检锁 [src/agent.embedcpu/BgeCpuEmbedder.cs:27-44] + `CapabilityScanner._scanned` 单次扫描门 [src/agent.registry/CapabilityScanner.cs:24-30]。
- **启动期零扫描**：索引在「首次查询」时加载（`File.Exists` → 读头 → 校验 version/payloadLen → 校验和 → 反序列化；任一步失败 → 判定失效 → 走重建，且**不阻塞**首查询）。
- 加载失败的降级与 `ThinkMemory` 同策略（损坏 → 空库/重建）[src/agent.exploration/ThinkMemory.cs:183-186]。

### 4.3 失效判据（现状空白，必须新做）

`Workspace._fileCache` 命中不校验 mtime [src/agent.workspace/Workspace.cs:155-167] 是既有的**脏读缺陷先例**，索引不得重犯：
- 逐文件 `(mtimeTicks, size)` 比对；不一致 → 只重算该文件条目（增量）。
- 全量重建需显式触发（用户指令 / 索引版本升级），**绝不因「巡检」自动全量**。

### 4.4 插件契约（I3 的「API 规范」）

复用既有契约（不新造）：插件 `ExecuteAsync(capabilityId="codeIndex.build", args=JSON) → PluginExecutionResult{Output=单行 JSON}` [src/agent/registry/CapabilityPlugin.cs:14-48]。
需补的三件（现状全无）：① **宿主注册点**（`Program.cs` 显式注册，AOT 禁反射 [src/agent/registry/CapabilityScanner.cs:33-35]）；② **能力清单/版本字段**；③ **请求/响应 DTO（STJ source-gen）**。
**待确认**：是否引入 manifest 文件与 `schema_version`（§8-Q2）。

### 4.5 与前端「页面显示优化」的接口（I2）

- 已有可复用：`SearchResult.MatchStart/MatchEnd`（高亮偏移）[src/agent.workspace/WorkspaceState.cs:188-195]、`HighlightContent` 500 字符截断 [src/agent.rag/RAGConfig.cs:770-786]、`Summary` 字段 [src/agent.rag/RAGConfig.cs:33]。
- 缺口：**无分页**（全库 0 命中）、前端仅 5 个 api（`chat.send`/`meta.ping`/`state.snapshot`/`state.hello`/`meta.info`）vs 文档 27 域 [docs/api.md:1371]。
- 建议 api 形状（待确认命名）：`index.search{query, limit, cursor} → {items[{path,line,matchStart,matchEnd,highlight,score}], nextCursor}`。

## 6. 验收标准（开发立项后适用）

| # | 验收点 | 判定方式（真断言，非「没测到」） |
|---|---|---|
| A1 | 启动零扫描 | 进程启动到 ready 期间，`Directory.GetFiles` 调用计数 = 0（探针挂钩或日志断言） |
| A2 | 首查询惰性加载 | 首次查询触发索引加载；第二次查询命中内存，**无重复反序列化**（计数器断言） |
| A3 | 加载校验生效 | 篡改索引文件 1 字节 / 截断 → 判定失效并重建，**不得**抛未捕获异常（单测） |
| A4 | 增量失效 | 改动 1 个文件 → 仅该文件条目重算（断言重算计数 = 1，其余条目对象引用不变） |
| A5 | 查询延迟 | 10 万条索引内存内查询 P95 < 10 ms（本机实测） |
| A6 | 引用图可用 | 对 3 个已知符号，插件返回边集与人工核对一致（人工 ground truth，至少 1 个反向引用） |
| A7 | 前端展示 | 一个真实 api 返回分页 + 高亮偏移，前端 DEMO 可渲染（沿用 `samples/FrontendApi.WinForms` 范式） |
| A8 | 不劣化 | 730/730 单测保持全绿；AOT 发布零 IL 警告 |
