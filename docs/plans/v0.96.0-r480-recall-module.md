# R480 计划 — 独立文本召回模块 (agent.recall)：极小常驻内存 + 数十 ms 召回

状态: 进行中
轮号: R480
工程形态: 独立模块工程 (不并入 agent.sln；成熟后再合回 agent 主项目)
用户令 (逐字): 「不需要百万文档，同比例压缩就可以，可以单独开个测试项目，只做文本召回的模块项目，可以参考第三方，等待检索能力成熟了在合并回agent主项目」
前序用户令 (逐字): 「另外有没有考虑过在超多文件系统和超大文本的环境下如何快速索引并召回关联内容的问题(不可以浪费内存或者仅用极小内存建立索引)的速度，一次调用前得在几十ms内吧」

## 1. 目标与判据总纲

1. 召回质量不退化：真实语料上 recall@10 达标（阈值见预注册）。
2. 常驻内存与索引体积脱钩：常驻 = 词表跳表 + 元数据；postings/正文/文档表一律按需 pread。
3. 单次调用前数十 ms：查询延迟 p95 在真实 1,299 文档档 ≤ 50 ms；由两点实测外推到 1e6 文档仍 ≤ 50 ms。
4. 增量保鲜：未变动目录整块剪枝，无脏时索引面零写入；有脏只重建脏文档。
5. 零反射 / AOT 安全 / 纯 BCL（无第三方运行时依赖）。

## 3. 磁盘格式（段 = 不可变，索引 = 段集合）

- `index.meta`：魔数 `ARECIDX1`、k1/b、分词配置（写入即成为查询侧唯一配置源）、段清单。
- `seg_x/`：`seg.meta`（含词表跳表：每 1024 词存 1 个顶部项）、`terms.bin`、`postings.bin`、`docs.bin`（含 `i64[count+1]` 偏移表）、`lens.bin`（定宽 i32 文档长度）、`text.bin`、`tomb.bin`。
- postings 区域 = 头 3 个 varint（docFreq/maxTf/块数）+ 块序列；每块 = `lastDocId`、`maxTf`、`nDocs`、`payloadLen`、payload（`nDocs × (delta, tf)`）。
- **块边界 delta 链重置**：每块首条 delta 为该文档的绝对 docId ⇒ 跳块不必解码被跳过的 payload（这是块级跳过正确性的前提）。
- 文档键命名空间：`0x01` 前缀 = 文档 Id、`0x02` 前缀 = 相对路径；正文 token 首字节 ≥ 0x21 或 ≥ 0xC2 ⇒ 不会冲突（读写两侧共用 `RecallKeys` 单一来源）。

## 6. 排除项（本轮明确不做）

1. 向量重排（bge 侧）：接口留空位，不在本模块实现（16–25 ms/文本，会把「数十 ms」预算吃光）。
2. 倒排压缩（PForDelta/roaring）：当前 varint + 块头已满足规模臂目标，压缩列为后续。
3. 段合并 / tombstone GC：本轮只做 tombstone 累积与判脏，合并列为后续（诚实边界）。
4. 并发写者 / 多进程写锁：本轮为单写者模型。
5. 跨段 BM25 统计精确性：idf 用索引级 N，avgdl 用段级 ⇒ 记录为近似（单段索引不受影响）。
6. 内容哈希校验档：指纹只取 (路径, size, mtime)，同 size 同 mtime 的替换检不出（需全量哈希档，列为后续）。

## 7. 设计增补 (用户令: 地址自描述 + 任务状态, 2026-09-16 OOB)

用户令 (逐字): 「跨文件跨url相当于不需要主动分类，但自己就包含了链接指向，比分类更靠谱，唯一的问题就是需要内容中自带链接地址或文件地址，相当于把分类能力交还给了用户和agent产出物，它比主动分类或建索引更好，而我们真正要做的就是产出物对于【探索】能力的双向优化，【探索】召回能精准执行，而agent产出物可以反哺优化，所以每个任务应该有个memory或当前状态？不应该仅靠上下文」

设计裁定 (可执行化):

1. **召回不做分类，做「地址携带 + 沿地址走」**：文档记录本来就带 `Path`（自身地址）；新增 `links.bin`（段级）承载**正文里已存在**的地址：markdown 目标 `](…)`、裸 URL（scheme 来自配置）、含 `/` 的相对地址（结构性判据，与后缀无关）。`RecallHit.Links` 在命中时按需 pread 返回。
2. **前提诚实标注**：链接覆盖度由产出方写入决定 ⇒ 只能召回「写过地址的产出物」；未写地址的产出物仍靠倒排词面命中兜底，两者都要有。
3. **双向闭环**（`RecallTaskState.cs`）：
   - 产出 → 状态：`RecallTaskStateStore.Append(taskId, event)` 把产出物地址/链接落到 `tasks/<taskId>.jsonl`（append-only，磁盘态，进程重启可读）。
   - 探索 → 状态：`RecordRecall(taskId, query, hits)` 把召回结果（命中地址 + 链接）写回同一任务状态。
   - 状态 → 可召回：`SyncToIndex(taskId, indexDir)` 把任务状态折叠成一条文档（地址 `task://<id>`，链接 = 产出物 ∪ 关联地址）回流进召回索引 ⇒ 下一次探索能命中它。
4. **不靠上下文**：状态是 `tasks/<taskId>.jsonl` 事件流 + 由它折叠出的物化视图（LastText / Artifacts / Links / EventCount），读取只需 taskId。
