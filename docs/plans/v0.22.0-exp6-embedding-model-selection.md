## 2. 关键前置发现：**瓶颈不在模型，在自研运行时**（实测对照，实锤）

同一 GGUF、同一评测集、同一台机器，两个运行时的对照：

| 运行时 | cos(相关对) | cos(无关对) | **margin** | 中文检索 top1 |
|---|---|---|---|---|
| llama.cpp（金标准） | 0.6354 | 0.2817 | **+0.1167** | **1.0** |
| 项目 `BgeCpuEmbedder`（托管） | 0.9559 | 0.9324 | **−0.0167** | **0.2**（=随机） |

- **判别力为零**：无关句与相关句余弦几乎无差（0.932 vs 0.956），检索 top1 退化到随机水平。
- 逐层 Trace 无塌缩（无 NaN/全零），但两个语义无关句 cos≈0.91 → 分歧点在前向/池化实现层，**不在模型**。
- **推论（本节是本档最重要的结论）**：换任何模型都带不走这个缺陷 —— 先把运行时修好，收益是**数量级**的（margin −0.017 → +0.117），远超换模型能给的边际（见 §4.1）。
- 证据：`/tmp/embbench/results.jsonl`、`/tmp/embbench/cs/Program.cs`(69 行 C# 同口径探针)、`/tmp/embbench/trace/Program.cs`(逐层诊断)。

## 3. 内存预算（用户关注点的直接回答）

**实测 RSS（llama.cpp，含计算缓冲）≠ 文件大小**，比值 1.7×~3.5×：

| 模型 | 文件 | **实测 RSS** | RSS/文件 | 占本机可用内存(2.2 GiB) |
|---|---|---|---|---|
| bge-small-zh-v1.5 | 25.2 MB | **87.8 MB** | 3.5× | 3.9% |
| bge-base-zh-v1.5 | 104.9 MB | **179.1 MB** | 1.7× | 8.0% |
| bge-m3 | 417.5 MB | **919.6 MB** | 2.2× | 41% |
| Qwen3-Embedding-0.6B | 609.5 MB | **1526.1 MB** | 2.5× | **69%** |

- 托管实现另有托管堆开销：同模型 `managed_mb=93.6`（R368 台账 `/tmp/bge_bench.log`）→ **自研路径的 RSS 只会更高**（同模型延迟托管/native ≈ 1.8×，§7）。
- **结论**：0.6B 级模型在 3.6 GiB 机器上"跑得起来"但**不可共存**（与 LLM host/worker、宿主进程争 2.2 GiB）→ 选型硬门槛：**RSS ≤ 300 MB**。

## 4. 统一口径实测对比（本机真跑）

**评测台**：`/tmp/embbench/bench.py`（语料=本仓 `src/**/*.cs` 切片）+ `bench_hard.py`（**硬检索集**：10 query × 8 **同域近似干扰项**，用于把模型分开 —— 简易集对 bge-small 已饱和 top1=1.0，无可分辨力）。
**口径**：llama.cpp server，`--threads 2`，bge 系 `--pooling cls`，qwen3 `--pooling last`。

### 4.1 主表（实测，非估算）
| 模型 | 长块延迟 | 短文本延迟 | 50 片段重排(估算) | RSS | margin | 硬集 top1 | top3 | MRR |
|---|---|---|---|---|---|---|---|---|
| bge-small-zh-v1.5 | 99.5 ms | 9.6 ms | **0.5 s** | 87.8 MB | +0.1167 | 0.60 | 0.90 | **0.737** |
| bge-base-zh-v1.5 | 420.6 ms | 58.5 ms | 2.9 s | 179.1 MB | +0.1281 | 0.60 | 0.80 | 0.723 |
| bge-m3 | 1064.0 ms | 127.7 ms | 6.4 s | 919.6 MB | +0.1664 | 0.50 | 0.90 | 0.687 |
| Qwen3-Emb-0.6B | 1648.9 ms | 233.0 ms | 11.7 s | 1526.1 MB | **+0.2333** | **0.70** | 0.80 | **0.795** |

- 「长块」= 386 字符均值切片（索引/建库口径）；「短文本」= ~30 字符（**查询期重排片段的真实口径**）。
- **延迟随文本长度 ~线性**（99.5 ms@386字 vs 9.6 ms@30字）→ 本框架"查询期按需重排若干片段"场景下，bge-small 的 0.5 s/50 片段是**可接受**的；base 已到 2.9 s。

### 4.2 质量维度：**统计不可分**（诚实口径）
- 硬集 n=10 query → **1 条 query 的差异 = 0.1 top1**；bge-small / bge-base / qwen3 之间的 top1 差 ≤0.1 = **落在单条噪声内**，不能宣称谁更强。
- 可确证的只有：**bge-m3 偏低**（top1 0.5、MRR 0.687，且代价最高）→ 明确淘汰。
- 因此选型**不能靠质量分决胜**，只能按「质量不可分前提下的成本」决 → §6。

### 4.3 权威榜单（旁证，口径不同，**不可与上表相加/混用**）
| 来源 | 指标 | 值 |
|---|---|---|
| BAAI 模型卡 | C-MTEB Average (56 数据集) | bge-small-zh-v1.5 **57.82** / bge-base-zh-v1.5 **63.13** |
| Qwen3 模型卡 | C-MTEB Mean(Task) | Qwen3-Emb-0.6B **66.33**；multilingual-e5-large-instruct 58.08；gte-Qwen2-1.5B 67.12；**ritrieve_zh_v1(0.3B) 72.71** |
- 榜单说 base 比 small 高 5.3 分，但**本机硬集上 base 并未胜出**（0.60 vs 0.60，MRR 反低）→ 榜单分不等于本场景可用性（榜单是长文检索/句对任务，本场景是**同域近似干扰下的短片段重排**）。
- 榜上还有两个**未测**候选（GGUF 可得，若需可补测）：`ritrieve_zh_v1`（0.3B，榜分最高）、`bekko-embedding`（25M，日语系 mmBERT）。

## 5. 换模型的真实成本（不是"换个文件"）

| 模型族 | 分词器 | 架构 | 本运行时（纯托管）改动量 |
|---|---|---|---|
| BERT+WordPiece（bge-*-zh-v1.5、gte-*-zh） | **已有** | **已支持** | **低**：把硬编码 4 层/8 头改为读 GGUF 元数据（~2 处） |
| XLM-R+SentencePiece（bge-m3、multilingual-e5、Conan） | 需新增 SentencePiece 解析 | 层数/250k 词表需泛化 | 中高 |
| Decoder+BPE（Qwen3-Emb、ritrieve_zh_v1） | 需新增 BPE | 需因果解码前向 + last-token pooling + MRL 截断 | **高** |
| ModernBERT（bekko） | 需新增 | 需新增架构 | 高 |

- 另有一条**非托管捷径**：把 llama.cpp 作为嵌入后端（native）→ 直接获得上表任意模型；代价是**放弃纯托管/AOT 单一发布形态**（与 R351/R353 钦定方向冲突）→ 需用户裁定。

## 6. 结论与推荐（三档）

| # | 结论 | 依据 |
|---|---|---|
| **R1** | **必做：修运行时实现缺陷**（与选型无关，且收益最大） | 同模型 margin **−0.017 → +0.117**、检索 top1 **0.2 → 1.0**（数量级）；换模型无法带来此收益（§2） |
| **R2** | **维持 bge-small-zh-v1.5**（本机口径下的最优点） | 质量与 base/qwen3 统计不可分；成本最低（延迟 1/4~1/24、内存 1/2~1/17）（§4.1/§4.2） |
| **R3** | **不建议**：bge-base / bge-m3 / qwen3-0.6B | base：无实测质量收益 + 4.2× 长块延迟；m3：质量最低 + 920 MB；qwen3：**1.53 GB RSS = 可用内存 69%** + 1.65 s/块 + 1.7× 延迟于 base |
| **R4** | **仅当用户真机显著强于本机**（≥8 GB RAM 且 ≥8 核）才考虑 0.6B 级 | 本机是 2 vCPU 共享实例，不代表用户真机；但需接受 native 后端或大改运行时 |

**一句话回答用户**：当前 bge 的"性能不足"**不是模型选错**，而是自研运行时判别力失效（更该修）；而"要不要换更适合的模型"——在本机 2 vCPU/3.6 GiB 口径下，**bge-small-zh-v1.5 就是最优点**，换更大的中文模型（base/m3/qwen3）不但质量上测不出优势，内存与延迟还要付出 2×~17× 的代价。

## 7. 诚实边界

1. **无用户真机数据**：本档全部延迟/内存来自本机（2 vCPU/3.6 GiB 共享实例）。若用户真机核数/内存更高，R3/R4 的天平会移动 → 需用户提供规格或真机复测。
2. **统计力弱**：硬集 n=10 query（±0.1 = 1 条），质量维度只能判"不可分"，**不能**判"谁更强"。
3. **口径不可混**：榜单分（C-MTEB 56 数据集/Mean(Task)）与本地硬集 margin/MRR 是两套口径，禁止相加或互推。
4. **native vs 托管**：§4 延迟是 llama.cpp（native）口径；同模型本项目托管实现慢 ≈1.8×（99.5 ms vs 181 ms，R368 读数）→ 若继续纯托管路径，上表延迟应视为**乐观下界**。
5. **未测候选**：`ritrieve_zh_v1`(0.3B，榜分 72.71)、`bekko-embedding`(25M)、`gte-multilingual-base` —— GGUF 均可得，按需补测（预计受 §3 内存门槛约束，0.3B 级同样吃紧）。
6. **C# 缺陷未定位到具体行**：只证伪了"模型不行"这一解释（§2），根因（attention/权重布局/归一化/池化）待 R370 逐层比对 llama.cpp 定位。
7. 本档**不含开发**：R1/R2 是否立项、R4 是否放宽形态约束，均待用户裁定。

## 9. R370 确定性召回实测复核（**推翻 §5/§8 的 10 条硬集结论**）

> 触发: 用户 R370 逐字「你需要实测它们用于召回的能力后再最终确定用哪个嵌入模型」。
> 口径: 冻结语料 **1299 块 / 384 文件**(项目真实源码+文档切片) + 冻结查询 **120 条**(LLM 生成, 强制不复述片段独特标识符, 生成后 ASCII 标识符过滤) + 冻结指标 recall@1/5/10/20 + MRR@10 + 词法基线(字符二元组 Jaccard)。

| 方法 | r@1 | r@5 | r@10 | r@20 | MRR@10 | 中位排名 | 平均排名 | 每块耗时 | RSS |
|---|---|---|---|---|---|---|---|---|---|
| **词法基线**(字符二元组) | **0.4417** | — | **0.7500** | — | **0.5583** | — | — | ~0 | ~0 |
| bge-small-zh-v1.5-q8 | 0.3083 | 0.5667 | 0.6333 | 0.7000 | 0.4150 | 4 | 237.78 | 88.2 ms | 106 MB |
| **bge-base-zh-v1.5-q8** | **0.4417** | **0.6667** | 0.7417 | **0.8000** | 0.5416 | 2 | 113.53 | 583.8 ms | 193 MB |
| bge-m3-q4km | 待补(上轮 503 掉队, 已修就绪判定后重跑) | | | | | | | ~1064 ms | 920 MB |
| qwen3-embedding-0.6b-q8 | 待补(同上) | | | | | | | ~1649 ms | 1526 MB |

### 结论（诚实更正）

1. **10 条硬集结论作废**：小样本(10 条)上"bge-base 未赢 bge-small(MRR 0.723 vs 0.737)"是**样本噪声**；在 120 查询/1299 块的判决口径下，**bge-base 全面领先 bge-small**(r@1 +13.3pt / MRR +12.7pt / r@20 +10pt)。
2. **纯稠密检索并不优于词法匹配**：bge-base ≈ 词法基线(r@1 打平, r@10 略低, MRR 略低)；bge-small 明显低于词法。→ 架构结论：**混合检索(词法倒排 + 稠密重排)才是正解**，纯稠密没有依据（互补性分析见 `eval/bge/complementarity.py`）。
3. **维持 bge-small 作为"训练基座"而非"终选"**：用户 R370 钦定「以确定性召回率为目标不断优化 bge-small-zh-v1.5」→ 基座固定 bge-small(25MB/88ms/106MB 成本优势巨大)，**用 T1 适配器把 r@1 往 bge-base/词法基线(≈0.44)逼近**；若适配后仍不达标，再讨论换基座(E6-Q2 复开)。
4. **§8 的 E6-Q1 已由本轮部分回答**：运行时判别力缺陷(C# 本地嵌入 margin −0.017)仍是最高优先靶点 —— 但注意：**它不影响本表的 llama.cpp 实测**（本表走 llama.cpp 金标准通路）。
5. **E6-Q4 复评**：m3/qwen3 在成本维度已被淘汰(920MB/1526MB RSS 对 2.2GB 可用内存)，补测只为"记录在案"，不改变选型。
