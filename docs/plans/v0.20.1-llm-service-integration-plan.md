> 本轮主题 (用户: "继续下轮迭代优化跑测任务"): 让已交付机制产生**真实收益**, 并闭合剩余缺口

## 0. 现状事实 (证据)

- `Program.cs` L~87-125: `--llm-service` (worker) 与 `--llm-manager` 分支已存在; 日志自写 (env `AGENTFRAMEWORK_LLM_SERVICE_LOG`)
- `RemoteEmbedder` 已实现但**框架内无调用点** (grep: 仅测试引用) → 机制空转, 无真实收益
- `ServiceCollectionExtensions` L226: `ITextEmbedder` 仍固定注册 `BgeEmbedder` (进程内加载 RSS ~157MB) 或 `NullTextEmbedder`
- 本地 LLM 推理 (`LocalLlamaCaller` / modelqueue) 仍在 CLI 进程内加载 — 与 bge 同源问题 (用户动因: "新CLI重新加载LLM到显存内")
- `/proc/meminfo` 为 Linux 专用 → 非 Linux 保守不卸载 (v0.20.0 已标注为待办)

## 1. 目标与范围

### P4-a 让 llm-service 在 CLI 内可用 (opt-in, 默认行为不变)
- 新增 env `AGENTFRAMEWORK_LLM_SERVICE_AUTOSTART=1` (或 `AGENTFRAMEWORK_BGE_MODE=remote|local`, 默认 `local`)
- 注册逻辑: 开关开启且 daemon 可用 → `RemoteEmbedder`; 否则原路径 `BgeEmbedder` (回退语义不变)
- **铁律遵守**: 默认零行为变化 (用户: "仅是新增本机 llm host 而非全面修改当前框架llm使用流程")
- 验收: 开关 on/off 各跑批测, 结果一致 (嵌入语义等价); CLI 启动 RSS 对比 (on = 不加载 bge)

### P4-b 本地 LLM 推理 worker 化 (评估 + 最小落地)
- 现状: `--llm-service` worker 只服务 bge embed; 本地 LLM 推理仍在 CLI 进程
- 方案: worker 增加 `{"op":"complete"}` (LLamaSharp 推理), manager 惰性拉起同一 worker (或按能力分 worker)
- 风险: 推理并发/上下文保持/KV cache 语义 → 需 plan 细化 (本轮到"评估 + 接口预留", 不盲目实施)

### P4-c 跨平台资源探测
- Linux: `/proc/meminfo` (现有)
- Windows: `GlobalMemoryStatusEx` (P/Invoke, AOT 兼容) 或 `GC.GetGCMemoryInfo().TotalAvailableMemoryBytes`
- 验收: 单测注入 + 文档标注

## 5. 实施记录 (R344, 进行中)

### 收益实证 (RSS, 同机同文本)
| 模式 | 客户端进程 RSS | 模型位置 |
|---|---|---|
| local (进程内 bge) | **160 MB** | CLI 进程内 |
| remote (llm-service) | **41 MB** | worker 进程 (153 MB, 全 CLI 共享) |
| manager 常驻 | 40 MB | 0 模型 |

→ **每 CLI 进程省 ~119MB**; N 个 CLI 并发仍只一份模型 (线性节省)。
