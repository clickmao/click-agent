# v0.31.0 · R409 —— 本地 prompt 模板闸门（结构性阻断）与 BOS 口径修正

状态: 已实施（R409，2026-09-14）

## 0. 问题拆解（先确认问题本身是什么）

「本地生成的 prompt 长什么样」此前完全由**调用方**决定：`LlamaCppProvider.GenerateAsync(string prompt)`
把手拼串直接 POST 到 `/completion`，代码里**没有任何地方**校验模板是否存在。

前提链（每步都有实测，不跳步）：
1. R409 探针（`eval/rover/r409/template-ab.md`）：38 B 裸文本 ⇒ 跑题循环、**不出 EOS**、无正解；
   96 B 出厂模板 ⇒ 正解 `144` + `stop_type=eos`。两侧 tps 18.53/18.66（不是速度假象）。
2. 缺模板的失败模式有**两种**：不答题；以及**不出结束符**（按 max_tokens=8192 计 ⇒ token 成本 ×20.5）。
3. 因此需要一道**不依赖调用方自觉**的闸门，且闸门本身不得是「启发式字符串猜测」。

## 2. 实测读数（原始文件在 `eval/rover/r409/`）

**2.1 模板来源对账**（`template_source_reconcile.out.txt`）：GGUF 内嵌模板（经 `/apply-template`）与归档
`eval/rover/tokref/r1_chat_template.jinja` 在 3/3 消息形状上**逐字节一致**（U=67 B/17 tok、S+U=95 B/23 tok、
U/A/U=112 B/26 tok，diff=0 B）⇒ 归档模板即 GGUF 内嵌模板，**K2b 模板来源漂移风险关闭**。
（自错披露：首轮我把 `2081`（字符）与 `2237`（UTF-8 字节）当成两个不同长度，误报「差 156 B」；单位错已纠正。）

**2.2 BOS 归属裁决**（`bos_ownership_probe.out.txt` + `verify-template.json`）：

| 输入 | add_special | token 数 | BOS 计数 | 首 4 id |
|---|---|---|---|---|
| 96 B 字面权串（sha `d1e94bf7…`） | true | **18** | **2** | 151646,151644,3838,374 |
| 96 B 字面权串 | false | 17 | 1 | 151646,151644,3838,374 |
| 67 B 渲染串（sha `25e467ee…`） | true | **17** | **1** | 151646,151644,3838,374 |
| 67 B 渲染串 | false | 16 | 0 | 151644,3838,374 |
| 38 B 裸文本 | true | 15 | 1 | — |

⇒ 规范形式 = **渲染串 + tokenizer 自动 BOS**（17）；「96 B 字面权串 + 默认 tokenization」= **双 BOS**（18）。
即：**BOS 归 tokenizer 管，字面注入即缺陷**。`/props` 给出 `bos_token`/`eos_token`/`chat_template`(2081 字符)
⇒ 闸门规则可**数据驱动**，不硬编码 id（`VerifyTemplateResult.BosId=151646` 由 BOS 文本自测得出）。

**2.3 产品通路对照**（`e2e-literal-path.json` / `e2e-chat-path.json`，同一权重同一题）：

| 臂 | PromptMode | prompt sha | tokens_evaluated | 生成 24 id | t/s |
|---|---|---|---|---|---|
| B 字面诊断通路 | `literal` | `d1e94bf7…`（96 B） | **18** | `151648,198,…,13` | 18.134 |
| A 渲染闸门通路 | `chat_template` | `25e467ee…`（67 B） | **17** | **逐位相同** | 18.119 |

⇒ 双 BOS 的实际代价：① 每次本地调用**多 1 个 prompt token**（17→18，+5.9%，K2）；② 两条通路**可复用前缀不是同一
token 流**（K2b：会话若跨通路，缓存前缀不可复用）；③ **不改变生成结果**（24/24 逐位相同）⇒ R408 的 24/24 对账
结论不受影响。计数证据：臂 B `LiteralPromptCalls=1`，臂 A `TemplateRenders=1`。

## 3. 闸门契约（结构性，非启发式）

端口化（可替换执行面）：
- `ILocalPromptRenderer.RenderAsync(IReadOnlyList<ChatTurn>, ct)` —— 唯一实现 `LlamaCppProvider`，
  经 `POST /apply-template` 由**服务端**按模型元数据内嵌 jinja 渲染 ⇒ 调用方**物理上无法手拼**。
- `LocalPromptGate.Validate(RenderedPrompt, ModelProps)` 四条规则：
  1. 来源必须 `GgufJinja`（否则 `prompt_not_templated`）；
  2. 渲染产物非空（否则 `prompt_empty`）；
  3. **不得字面包含 BOS 文本**（否则 `prompt_literal_special_token`）；
  4. **不得以 EOS 文本结尾**（否则 `prompt_literal_special_token`）。
- 规则 4 是被实测**修正**过的：初版写成「不得包含 EOS」，多轮渲染（118 B，含 EOS 轮分隔符、不以 EOS 结尾）
  会**误拦合法输入** ⇒ 改为「不得以 EOS 结尾」。这正是「规则先过合法样本」的必要性。

## 6. 排除项（本轮不做，明确不承诺）

- 不做**产品级会话历史装配**：闸门只保证「给了 messages 就必然经模板渲染」，会话/skills/history 的拼接策略不在本轮。
- 不做**远端 Jinja 与本地 GGUF jinja 的跨实现字节对账**（本轮只对齐了归档模板 ≡ GGUF 内嵌模板）。
- 不做**字面通路删除**：R408 的 id 级对账需要它，保留为显式诊断通路（有计数、有命名警告）。
- 不做 p7b/Lean 分支与闸门的联动（p7b 已删除）。
- 不改 `aot_check_policy`（`release_tag_only`）。

## 7. 遗留 / 下轮候选

1. **会话前缀落点**（K2b 真正的大头）：本地调用必须挂在会话稳定长前缀之后，否则可复用前缀覆盖 ≈0.43%。
2. 把闸门推广到**远端 provider**（同一契约、不同渲染实现）——需先解决跨实现在对账（钉精度档 + 同 messages）。
3. `LlamaCppProvider` 的 `--embeddings` 与生成互斥 ⇒ 进程形态编排仍未固化。
4. `VerifyTemplateResult` 可增「多轮 + 长前缀」形状（当前只验单轮）。
