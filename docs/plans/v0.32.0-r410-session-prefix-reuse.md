# v0.32.0 · R410 —— 会话长前缀复用（K2b 落点）与生成口径分离

状态: 已实施（R410，2026-09-14）

## 0. 问题拆解（先确认问题本身）

「K2b（缓存命中 ≥97%）在本地通路上能否达标」不是一个问题，而是三个可分别验证的前提：

| 前提 | 内容 | 此前状态 |
|---|---|---|
| P1 机制 | 服务端有前缀缓存，同前缀第二次请求能命中 | 未验证（只在 R407/R408 的对账口径里**关掉**了缓存） |
| P2 长度 | 可复用前缀的**绝对长度** ≥ 4224 token（K2b 红线口径） | 未验证（短独立 prompt 的绝对复用长度从未记账） |
| P3 生命周期 | 缓存跨调用存活（同一 server 进程内） | 未验证；且本地生成通路**只存在于 E2E CLI**（每次调用新起 server） |

并且：**P2 是绝对长度问题，不是比值问题** —— 短 prompt 的「复用比」可以很高（17/18），但对 4224 红线的覆盖只有 0.4%。把比值当 KPI 会得出相反结论。

## 1. 判据（开跑前预注册）

- **J1** 会话形态（长前缀 + user）第 2 次同前缀请求：`cache_n / prompt_n ≥ 0.97`
- **J2** 短独立 prompt（R409 权威 96B 形状）：绝对 `cache_n << 4224`（结构上不达标）
- **J3** 负控（前缀首 token 改变）：`cache_n` 必须归零
- **J4** `cache_prompt=false`：`cache_n` 必须恒为 0（⇒ 对账口径与生产口径必须分离）

读数来源：llama-server `/completion` 的 `timings.cache_n / timings.prompt_n`（**服务端自报**，非估算）。

## 2. 实测摘要

- 同 server 内：4255 token 长前缀第二次请求只重算 **5 token**（`cache_n=4250`，复用率 **0.9988**，墙钟 233.9 s → **0.5 s**）。
- 短形态：绝对 `cache_n=17` ⇒ 对 4224 红线覆盖 **0.402%**。
- 负控与关缓存：`cache_n=0`（两条都按预期）。
- 跨进程（产品 CLI 每次新起 server）：即便 `--reuse on` + 稳定 487 token 前缀，`CachedTokens=0`、`SessionCacheMisses=1`。

完整读数与原始文件见 `eval/rover/r410/r410-evidence.md`。

## 3. 设计

1. **口径分离**：`CompletionReuse { Session, Reconciliation }`。`GenerateAsync` 默认 **Session**（生产口径，开前缀缓存）；对账必须显式传 `Reconciliation`。
2. **唯一映射点**：`CompletionProfiles.Build()` —— 口径 → 请求参数只在这一处决定（可单测，防口径散落成多处 if）。
3. **记账**：`CompletionResult.CachedTokens`（服务端 `cache_n`，非估算）+ 三个被使用计数。
4. **静默失效可见化**：会话口径下 `prompt ≥128 token` 且 `cache_n=0` ⇒ `SessionCacheMisses++`（跨进程复用为 0 这类缺陷会自己暴露，不靠人查）。
5. **会话入口**：`agenthost --llamacpp --system-file <f> --chat-text <s> --reuse on` —— 长前缀与 user 轮同处一个 message 列表（K2b 的复用对象）。
