# R469 计划 · 命中率**理论上限分档**：把用户轮长度从命中率分母里剥离

- 轮号: R469（本侧主线轮，**纯测量/口径轮**，零产品行为改动）
- 状态: 已收口（R469）
- 上游: R468（真实流量组成：可跳面 0.00% / 90.2% 轮必走远端）⇒ 真实 KPI 唯一杠杆 = 单次调用 token
- 代码事实: `src/agent.modelqueue/LocalGenerationPort.cs`（门判/承接，**本轮未改**）；桩侧落盘 `eval/rover/r467/calls-*.jsonl`（`messages[]` 全量 = 外部真值）
- 产物: `eval/rover/r469/{prefix_stability.py, prefix_stability_r467.json, prefix_stability_negctl.json, hit_ceiling_bands.py, hit-ceiling.json}`

## 1 问题
97% 命中率红线（R461）一直以「前缀 3.1k ⇒ 新增 ≤93.5 tok」形式单值报出，但从未问：**新增部分是用户自己的话，能否被任何注入策略压到 93.5 tok 以下？** 若不能，则红线对一部分轮**结构性不可达**，必须分档声明而非当作可达目标。

## 2 口径（本轮预注册，先落盘后跑复现）
- `prompt_k = prefix_k + new_k`；`prefix` = 与上一次调用**逐字节公共前缀**（可缓存）；`new` = 其余（不可缓存）。
- 命中上限 `= prefix / (prefix + new)`。红线 = 0.97 ⇔ `new ≤ 0.03093 × prefix`。
- 用户轮 token 估算沿用 R461 `FormalPromptContract` 口径（中文 ≈ 1 token/字）。

## 3 预注册判据
- **C1** 主调用对逐字节 **tail-only** 稳定率：R 臂必须 5/5（`prefix_share == 1.0` 且 `tail_only`）。
- **C2** 分档表落盘：每档（用户轮字符 0–30 / 31–93 / 94–200 / 201+）给出轮数、占比、中位用户 tok、三档前缀（2,110/3,000/4,000）下的命中上限、以及「达 97% 所需最小前缀」。
- **C3** 长档（用户轮 > 93.5 tok）必须显式标注**结构性不可达**，不得以单值 97% 报 KPI。
- **C4** 负面控制：动态字段注入 system 首段 ⇒ 前缀占比必须**显著下降**（正控=纯尾部追加 ⇒ 占比 1.0）。
- **C5** 口径声明：分档表仅用**无 `src` 标记**的真实轮（400 条），网格/InlineData 行另行标记、不得混入。

### 4.3 C4 负控（`prefix_stability_negctl.json`）
正控 tail-append `share=1.0` / `tail_only=true`；负控（system 首段注入动态字段）`prefix=407`（`share=0.7918`，分歧位置靠前）⇒ 指标响应且非恒真（`verdict=PASS`）。

## 5 约束与排除项
- 不改产品 `src/**`；不起 llama-server；不做远端调用；不 push。
- 用户轮 token 为**估算**（1 token/字），真实计费面另有 k=1.221（见 R465 `real_billing_probe.py`）——本轮不外推绝对成本，只给**占比**。
- 前缀大小取自 R467 实测 2,110 tok 起点；3,000/4,000 为假设档，用于展示单调性。

## 6 验收
C1–C5 全绿 + `hit-ceiling.json`/`prefix_stability_*.json` 落盘 + 形式门禁无新红。

## 7 诚实边界
① 分档表的「命中上限」是**上界**（假定前缀 100% 可缓存且供应商按前缀计费），不是实测命中率；② 推测的未来前缀档 3,000/4,000 未在真机验证；③ 微调用/判官调用与主调用**同槽竞争**导致缓存驱逐的假设，本轮只给出「交错存在」的事实，未做真机 `cache_n` 归因（R470 候选）；④ 用户轮 token 换算 1 字≈1 tok 对英文/代码轮会低估。
