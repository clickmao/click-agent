# v0.21.0 Role 系统计划（可成长扮演角色）

> 状态：**待用户确认后实施**（本计划为设计+工程文档，未动产品代码）。
> 撰写轮次：R359（2026-09-11）。作者口径：现状代码事实（带行号/文件）→ 设计 → 关键约束 → 验收标准 → 排除项。
> 术语约定：**Role** = 可加载、可成长、可切换的"扮演角色"数据包；与现有 **AgentProfile**（行为统计画像）互补而非替代。

## 0. 用户钦定需求原文（逐字保留）

> 结合现有模块能力，总结出一套可用在该CLI内的专用的 可成长的、扮演角色性格有区别的（LLM内输出可能因为角色画像语风不同与当前说明的性格在人观感上有体验）、能力有区别的（可能是绑定了二级数据召回来源擅长部分不同）、有自身倾向的（会根据Role内数据对问题产生评估问题且可能持有怀疑）和成长经历（和上下文压缩类似，某些鲜明的多次的强烈的记忆会产生记录并长期维持不变）、数据模型（需要数据紧凑，压缩后体积很小）和操作模型与API，撰写报告和使用说明和实施开发工程并更新全部已有说明文档，有点类似目前CLI使用的数据来源依凭的二级挂件组的感觉？

拆解为 6 个可验收能力：

| # | 能力 | 验收锚点 |
|---|------|---------|
| R1 | 性格有区别 | 不同 Role 的 system prompt 语风块不同；同题问答观感可辨（评测断言） |
| R2 | 能力有区别 | Role 绑定二级召回来源（不同向量库目录/知识域），擅长面随 Role 切换 |
| R3 | 自身倾向 | Role 内置「倾向规则」对输入产生评估性提问/怀疑标记（不盲从用户前提） |
| R4 | 成长经历 | 鲜明/多次/强烈的交互记忆沉淀为 Role 级长期经历，跨会话维持不变 |
| R5 | 数据模型紧凑 | Role 包落盘体积小（目标：基础包 ≤ 8KB，含经历 ≤ 64KB）；加载零反射 |
| R6 | 操作模型与 API | `/role` 指令族 + `role.list/role.use/role.info` FrontendApi 域 |

## 2. Role 数据模型（R5 紧凑性设计）

### 2.1 双文件包（对齐 SKILL.md 包模式）

```
roles/
  skeptic/                  # Role 目录 = role id
    role.yaml               # 结构化头（机器读）
    PROFILE.md              # 人格语料（LLM 读; 人可写可改）
    growth.jsonl            # 成长经历（追加式 JSONL, 运行时写）
```

### 2.2 role.yaml（结构化头，MiniYaml 解析——与 skill.yaml 同解析器）

```yaml
id: skeptic
name: 疑问者
version: 1
language: zh
# —— R3 倾向规则（评估器输入; 数量克制: 建议≤5条） ——
biases:
  - id: doubt-premise        # 怀疑未证明前提
    trigger: claim_without_evidence
    action: ask_evidence     # 产出评估性提问而非顺从
  - id: prefer-data-source
    prefer_recall: internal/design-docs   # R2: 擅长域绑定
# —— R2 能力绑定（二级召回来源） ——
recall:
  - source: vectormemory://data/recall/design-docs
    label: 设计文档域
    weight: 1.0
  - source: vectormemory://data/recall/common
    weight: 0.3
# —— R1 语风参数（喂给 LLM 的渲染开关） ——
voice:
  tone: probing            # 追问型/沉稳型/活泼型…
  max_questions: 2         # 单轮评估性提问上限
  emoji: false
# —— 紧凑性预算（加载时强制校验） ——
budget:
  profile_max_chars: 2048  # PROFILE.md 渲染上限
  biases_max: 5
  recall_max: 4
  growth_max_entries: 64   # 成长经历条数上限
  growth_max_chars: 32768  # 经历总字符上限（≈32KB）
```

### 2.3 体积预算（R5 验收数字）

| 组成 | 上限 | 说明 |
|---|---|---|
| role.yaml | ≤ 2KB | 结构化头 |
| PROFILE.md | ≤ 2KB 源 / 渲染 ≤ 2048 chars | 人格语料 |
| growth.jsonl | ≤ 64KB（64 条 × ~512B） | 运行时增长，超限触发 RoleCompress |
| **基础包合计** | **≤ 8KB** | 不含经历 |
| **满载合计** | **≤ 64KB+4KB** | 含满额经历 |

- 落盘即压缩后体量：growth.jsonl 每条为一条 `{"t":tick,"k":kind,"s":score,"x":≤256ch}` 紧凑行（键名单字符化），**不做** GGUF 级二进制（复杂度不划算，64KB 已足够小）。
- 渲染进 prompt 的 Role 块预算：**≤ 1200 chars**（语风 300 + 倾向 300 + 经历 top-6 × 100），由 `RoleRenderer` 强制截断——防 Role 挤占主上下文。

### 2.4 成长经历条目模型（R4）

```json
{"t":1234,"k":"milestone|stance|lesson","s":0.87,"x":"用户纠正过：X 的前提是 Y，此后对此类问题先问 Y"}
```

- `k` 三类：`milestone`（强烈事件）/`stance`（立场沉淀，可被 R3 倾向引用）/`lesson`（教训/偏好）。
- `s` = 强度分（0~1）：由「重复次数 + 用户显式纠正 + token 规模」加权（判定规则见 §3.4）。
- **长期维持不变**：`stance` 类条目只有用户显式纠正才允许覆盖（写 `supersede` 标记，旧条不删、标记失效）；`milestone/lesson` 遵循滚动淘汰但淘汰时需 `s` 低于中位数。

## 3. 运行时设计（R1-R4 落地点）

### 3.1 RoleRegistry（新，`src/agent.roles/RoleRegistry.cs`，零内部依赖对齐 embedcpu 原则）

- `LoadFromDirectory(root)`：目录扫描 + MiniYaml；坏包跳过并 `AgentTelemetry.Emit("role_load", ...)`（对齐 SkillRegistry `:36` 降级原则）。
- 预算校验：超预算的包**拒载**（报错明确到字段），防膨胀失控。

### 3.2 语风注入（R1）

- `RoleRenderer.RenderVoice(role)` → 300 chars 语风块，插入点 = `IndustrialAgentV2.cs:1949` 的 blocks 列表（新增一个 `RoleRendered` block，排在 agent 画像之前——角色人格优先于行为画像）。
- 语料写作规范进使用说明：PROFILE.md 必须是「示例对话 + 第二人称守则」，禁止抽象形容词堆砌（LLM 对示例的模仿远强于对标签的服从）。

### 3.3 能力绑定（R2）

- Role.recall 声明 → `ContextGradient` 组装时把该 Role 的召回源列表置于默认源之前（weight 排序）。
- 召回失败/目录不存在：降级到默认源并打点 `role_recall_fallback`（不阻断主链）。

### 3.4 成长判定（R4）

- 会话轮结束时（V2 管线尾部，现有打点区 `:1176` 附近）跑 `RoleGrowthEvaluator`：
  - 强度分 `s = 0.4×repeat + 0.4×correction + 0.2×salience`；
  - `repeat`：同主题跨轮出现 ≥2；`correction`：用户否定/纠正了 Role 上一轮输出；`salience`：该轮 token 量/情绪词启发式。
  - `s ≥ 0.6` → 写入 growth.jsonl（去重键 = 主题 hash）。
- **RoleCompress**（对齐上下文压缩哲学）：growth 条数 > 64 时，同类 lesson 合并、`s` 低的 milestone 淘汰，`stance` 永不自动删。

### 3.5 倾向评估（R3）

- `RoleBiasEvaluator`：输入用户消息 + biases 规则 → 命中 `doubt-premise` 类规则时，在 prompt 中附加一条「评估指令」（要求 LLM 先列前提再回答），并在回复后处理中**检测 LLM 是否提出了评估性问题**（用于评测断言，不做硬拦截）。
- 持有怀疑的表现形式是**提问与前提澄清**，不是拒绝回答——此为产品语义边界（写进使用说明）。

### 3.6 操作模型与 API（R6）

**CLI 指令族**（对齐 `/model` 家族风格，`IndustrialAgentV2.HandleModelCommand` 同款分支模式）：

```
/role list            # 列出 roles/ 下全部包（含体积/经历数）
/role use <id>        # 激活（会话级; 写入 profile 持久偏好）
/role off             # 回到无角色默认态
/role info [id]       # 渲染预览（当前 prompt 块实况 + 经历 top5）
/role forget <id> <hash|all>   # 经历删除（用户数据权）
```

**FrontendApi 域**（契约 v1 不破坏，新增 api）：

```
role.list   → {"roles":[{id,name,active,size_bytes,growth_entries}]}
role.use    → {"id":"skeptic"} → {"ok":true}
role.info   → {"id":"skeptic","voice":...,"biases":[...],"growth_top":[...]}
```

**DI/装配**：`ServiceCollectionExtensions` 注册 `RoleRegistry`（单例）+ `RoleRenderer/Evaluator/Compressor`（无状态静态类亦可）。

## 4. 关键约束（非协商）

1. **AOT 铁律**：Role 包解析走 MiniYaml/STJ source-gen（`JsonSerializerContext`），零反射；发布 0 IL 警告验收。
2. **默认行为不变**：不激活 Role 时，全部管线与 v0.20.5 完全一致（回归断言：无 Role 激活时 prompt 中不含任何 Role 块）。
3. **Role 永不改写用户数据**：growth.jsonl 只增/合并/淘汰，删除仅经 `/role forget`。
4. **预算即法律**：所有渲染进 prompt 的 Role 内容超预算即截断+打点，不静默膨胀。
5. **文档同步义务**：交付时同步更新 README 能力段、`docs/CLI指令说明.md`（/role 家族）、FrontendApi 契约文档。

## 5. 验收标准

| 项 | 断言 |
|---|---|
| A1 紧凑 | 附带 2 个示例 Role 包（probing 疑问者 / steady 沉稳者），基础包 ≤ 8KB 实测 |
| A2 语风 | 同题（"为什么天空是蓝的"）双 Role 回复在语风断言（疑问句占比/句长分布）上可区分 |
| A3 倾向 | 含未证前提的输入（"既然 X 已成立…"）触发评估性提问 ≥1 次（probing Role） |
| A4 成长 | 3 会话重复同一纠正 → 第 3 次起 Role 直接携带该 lesson 回答；重启进程后仍生效 |
| A5 隔离 | 切换 Role 后二级召回源列表随切（可从打点证实）；无 Role 时与 v0.20.5 行为逐字节一致 |
| A6 API | /role 5 条指令 + FrontendApi 3 api 真机 E2E 全通 |
| A7 回归 | 全量测试绿（现 683+ 基线不降）；AOT 0 IL 警告 |

## 6. 排除项（本版不做）

- 不做 Role 间对话/多 Role 同会话。
- 不做 Role 云端市场/分发签名。
- 不做情绪状态机（stance 是立场不是情绪）。
- 不做 PROFILE.md 的 LLM 自动生成（工具辅助校验可以有，生成本版手写）。
- FrontendPromptService 的 ask 域审批路由（P2 既定）不并入。

## 7. 待确认（下次开发前问一次）

1. growth.jsonl 强度判定中 `salience` 的启发式是否可接受（备选：改为纯 LLM 自评，代价是每会话尾多一次 LLM 调用）。
2. `/role use` 是会话级还是进程级持久（本计划默认：写 profile 持久，`/role off` 显式关闭）。
3. 示例 Role 的两个人格是否需按用户真实使用场景定制（当前按通用演示写）。
