## 3. 推荐设计（探索结论）

### 3.1 工作目录判定器（先决条件，最小实现）

```
WorkspaceLocator.Resolve(cwd) → { Kind: Project|Bare, Root: string?, Marker: string? }
判定顺序: ① 显式配置 (--workspace / env AGENTFRAMEWORK_WORKSPACE) 
        ② 向上找 .git / *.sln / *.csproj 目录 (首个命中即项目根)
        ③ 均无 → Bare (无工作目录) → 仅影响教训记录的 Scope 标记 (Project|Session), 不影响教训表存亡
```
- 判定结论要**可观测**（telemetry 点 + `state.snapshot` 字段），否则又变成"隐式行为"。
- **R369 更正后口径**：教训表是 **role 模块资产**（§8-1），**不因无工作目录而不存在**；工作目录判定仅用于 ① 给记录打 `Scope: Project|Session` ② 决定"项目相关教训是否为该 role 记录"。原"不落盘/内存态"降级**只适用于 Project 作用域的项目相关记录**。**必须显式实现，不许靠 cwd 兜底**。

### 3.2 教训表（L1）—— 以 `ExecutorLessonMemory` 为内核补一层统一面

- **不搬迁数据**：新建 `LessonsTable` 作为**统一读面 + 事件源**，三源（ExecutorLessonMemory / FailureClusters / GuardrailMemory）通过**适配器**投影为统一记录，避免大爆炸式迁移。
- 统一记录字段（最小）：
  `{ Id: 稳定指纹(FNV-1a, 复用 R365 算法), Kind: Execution|Failure|Guardrail|Correction, Pattern, Count, FirstSeen, LastSeen, Solution?, Source: 组件名, Scope: Project|Session }`
- **（R369 用户钦定）教训必须是语言无关的通用工程教训**：`Pattern` 承载的是**缺陷模式 / 前提条件 / 失效机制 / 可验证判据**，不是某语言某工具的操作口诀。语言与工具**只能**出现在实例字段里：
  `{ Id, Kind, Pattern: 通用模式文本, Precondition?, Mechanism?, Verify: 可复现判据, Count, FirstSeen, LastSeen, Solution?, Scope, Instances: [{ Lang, Tool, Evidence, SeenAt }] }`
- **身份铁律**：`Id` 指纹只对**通用化后的 `Pattern` + `Kind`** 计算 —— 语言名/工具名/专有 API 名**不得进入指纹输入**。否则同一条通用教训会被拆成 N 条语言专属教训，跨语言零复用，教训表退化为"某语言的踩坑清单"。
- 键稳定性铁律：指纹必须**跨进程/跨 locale 稳定**（FNV-1a + 序数排序，R365 已实证踩坑），禁用 `string.GetHashCode()`。
- **归属（R369 用户钦定，两度更正后的最终口径）**：教训表是 **role 模块（`src/agent.roles/`）的资产** —— 表本体、**提交（写入）API**、读取面**全部归 role 模块**，不与 agent 全局层/任务层混放。
- 落盘：`data/roles/{roleId}.lessons.json`（与既有 `data/roles/failureClusters.json`、`data/roles/{id}.growth.json` 同域，对齐 role 运行时数据约定）；STJ 源生成，禁手写 StringBuilder；写入走**原子写**（tmp+rename，同 `.rbin` 先例）。
- **无 role（`ActiveRole=null`）语义**：与 R365 失败簇注入门控一致 —— 候选 ① 不落盘不注入（推荐）② 落匿名 role 待归并；见 §8-7。

### 3.3 API 面（L4）—— **读写 API 均归 role 模块**

> R369 用户钦定：**提交（写入）API 与读取 API 同属 role 模块**（`src/agent.roles/`）。宿主/CLI/前端只依赖 role 模块暴露的接口，**不直连教训文件**。

| API | 归属 | 语义 |
|---|---|---|
| `RoleLessons.Submit(record)`（模块内唯一写入口） | `src/agent.roles/` | 教训提交（去重/计数/升级在此完成） |
| `role.lessons.query { roleId?, since?, kind?, scope?, limit? }` | `src/agent.roles/` | 拉取（增量游标 = 版本号） |
| `role.lessons.detail { id }` | `src/agent.roles/` | 单条详情 |
| 域登记 | `frontendapi`（只做转发） | `meta.info.domains` 增 `role`/`role.lessons` 子域（当前硬编码 3 域必须改） |
| `state.snapshot` | `frontendapi`（读 role 模块版本号） | 增 `lessons_version`（单调递增 → "有新教训"） |

> 域名待确认（§8-8）：`role.lessons.*`（显式归属）vs `lessons.*`（简短）。

### 3.4 前端通知（L5）—— 两条路，建议先做 B

- **方案 A（真推送，P2）**：frontendapi 增加客户端注册表 + `FormatEvent` 广播 + 订阅/游标。改动面大（连接生命周期/背压/断线重连），且与既有 P2 路线图一致。
- **方案 B（推荐先做，零协议破坏）**：复用 `state.snapshot` 的**拉取式**语义 —— 暴露 `lessons_version`，前端轮询到版本变化即拉 `lessons.query?since=`。这与现状架构完全兼容，且"新教训已到达"语义成立（版本号变化 = 到达事件）。
- **方案 C（与既有 `@cmd` 通道打通）**：`@cmd` 已是 agent→前端单向通道，但**不带 req_id/ack**，且未接 `CommandWriter`；可作为"轻提醒"（"有新教训"），细节仍走 query。
- 建议：B 先落地（可验收、低风险），A/C 记为后续（本文档 §8 待确认）。

### 3.5 L2（"是否在本项目创建"）—— **R369 已作废，不再问询**

- 用户钦定教训表为 **role 模块资产** → 不存在"是否在用户项目内创建"的问题，**不新增问询**；`IUserPromptService` 不参与本项。
- 降级为可选的一问：role 自身是否启用教训记录（`--lessons on/off` 或 role 配置位），**但不按项目向用户提问**。
- 与 staging 审批链的关系不变：**审批 = 单次动作授权**，教训记录 = role 的长期资产，两者不复用同一存储。

## 4. 关键约束

1. **指纹稳定性**：FNV-1a + 序数排序（R365 教训，跨进程/跨 locale）。
2. **零反射 / AOT**：STJ 源生成；禁手写 JSON 拼接（既有 `ExecutorLessonMemory` 属技术债，若扩用需先修）。
3. **原子写**：教训表落盘 tmp+rename。
4. **诚实边界**：教训"命中"必须绑真实事件（真实失败/真实纠正），不许 LLM 自述"我学到了"就记一条。
5. **隐私**：`ContextTail` 类字段截断上限（既有 `count>=8` 才补 `[:37-38]` 的设计保留），且不外发原始对话。
6. **零 shell**：不涉及。
7. **教训通用化（R369 用户钦定，铁律）**：任何执行语言（Python / C# / C++ / Shell / JS…）产生的原始观察，入库前必须先经**语言剥离抽象**：
   `原始观察（含语言/工具专名） → 抽象（剥掉 API/语法/工具名，保留「前提 → 失效机制 → 验证判据」骨架） → 归并（按通用 Pattern 去重计数） → 原文证据落 Instances[]`。
   - 反例 → 正例（写法规范，全文一致）：
     ❌「`py_compile` 只到语法级，不算验证」→ ✅「**静态语法校验不覆盖运行期语义**，交付前须补**运行级验证**（实例：Python `py_compile`、C# 编译通过、C++ `-fsyntax-only`）」
     ❌「C# 里 `List` 成员要加锁」→ ✅「**共享可变容器在多线程下须整体加锁**（实例：C# `List<T>`+`lock`、C++ `std::vector`+`mutex`、Go slice+`sync.Mutex`）」
     ❌「`string.GetHashCode()` 跨进程会变」→ ✅「**哈希/排序不得依赖运行时随机化或区域设置**，须用稳定算法（实例：.NET `string.GetHashCode`、Python `PYTHONHASHSEED`、C++ `std::hash` 实现差异）」
     ❌「bge 的 GGUF 4 层 8 头要硬编码」→ ✅「**模型结构参数必须从元数据读取，不得按单一实例硬编码**（实例：GGUF 层数/头数、ONNX 输入形状）」
   - **可机检判据**：入库记录的 `Id`/`Pattern`/`Kind` 中不得出现语言名、文件扩展名、专有 API 名（黑名单词表 + 词法检查）；命中即视为未抽象 → 拒绝入库或强制降级为 `Instances` 字段。此检查是**开发验收项**（见 §5 A8）。
   - 收益（同时是验收依据）：同一条通用教训应能被**任意语言**的后续任务命中（`Count` 跨语言累加）。

## 5. 验收标准

| # | 断言 |
|---|---|
| A1 | 同一 pattern 出现 3 次 → 表内 1 条记录 `Count=3`（去重成立），第 4 次命中 `Solution` 升级 |
| A2 | 进程重启后指纹不漂移（同 pattern 命中同一条）—— 跨进程用例锁死（R365 同类回归） |
| A3 | `LessonsTable` 写入成功 → `lessons_version` 自增，`lessons.query?since=` 能拉到增量 |
| A4 | **归属 role**：教训表落 `data/roles/{roleId}.lessons.json`；挂载 role 后读写均可用，**不写用户项目目录**；无 role（`ActiveRole=null`）时按 §8-7 口径（默认不落盘不注入），结论进 telemetry/snapshot |
| A5 | **负断言 ×2**：① 运行后**用户项目目录零新增文件** ② **跨 role 隔离**（role A 的教训不出现在 role B 的查询结果里） |
| A6 | 前端侧：轮询 `state.snapshot.lessons_version` 变化 → `lessons.query` 得到新条目（端到端脚本证据） |
| A7 | 全量测试绿 + AOT 0 IL 警告 |
| A8 | **教训跨语言归并（R369 钦定）**：构造同一通用模式的两个实例（不同语言/工具：如「静态检查 ≠ 运行验证」的 Python 与 C++ 两例）→ 表内 **1 条**记录 `Count=2`、`Instances` 两项；**负断言**：`Id`/`Pattern` 中**零**语言/工具专名（黑名单词表机检） |

## 6. 排除项

- 不做教训的自动向量检索（不在本项；与探索项 1 的 bge 分层同域，另行评估）。
- 不迁移/废弃既有 6 个存储（只做统一读面 + 适配器）。
- 不做 P2P/多机教训同步。
- **不做 agent 全局层的教训表**（R369 钦定归属 role 模块；全局层不得另存一份）。
- **不做语言专属教训表/标签体系**（R369 钦定教训必须通用化；语言只在 `Instances[]`，不得作为分类维度或指纹输入）。
- 不做真推送（方案 A）的首期实现（见 §3.4）。
- 不动 `CorrectionDetector` 的赏罚语义（与探索项 3 §3 边界一致）。

### 10-1 `heuristic-boundary-anchoring` —— 启发式边界的"强弱证据"分离
- **前提**: 需要从自由文本里**提取结构化块**(代码/配置/日志段), 而源文本没有显式分隔符(无围栏、无标签)。
- **失效机制**:
  1. 用"**连续/相邻**"当边界判据 → 弱 token(空行、注释、字符串字面量内部文本)会把无关内容并入块;
  2. 用"**整体占比**"当准入闸门 → 文档健全的产物被自身注释/文档字符串拖累, 比例超阈值被**误拒**(真机: 3 连跑中 1 次优质实现被判"散文过多"而放弃提取)。
- **正确形态**: ① 边界锚定在**最后一个确证项**(强证据), 弱证据只能附着、**不得**通过相邻性传递; ② 分类器必须**词法感知** —— 字符串字面量/注释内部的行不是自由散文, 须按词法状态机归入中性; ③ 闸门从"散文 vs 代码"改为"**确证项计数 + 内部散文占比**"。
- **验证判据**: 负向控制(纯散文 / 片段过短 / 已有显式分隔符)必须**零误报**; RED 控制(关闭机制→用例必红)必须现场跑过。
- **Instances**: `src/agent/registry/SegmentKind.cs`(三引号状态机 + `Promoted` 归因); 机检 `UnfencedCodeDetectionTests` 9/9 + RED 3 红。

### 10-2 `budget-exhaustion-is-not-success` —— 预算耗尽不是成功
- **前提**: 生成式调用输出预算有限(`max_tokens`), 而调用只回报"传输层成功"。
- **失效机制**: 成功判据只看传输层(HTTP 200 / `success=true`)或只看"正文非空" → **半份正文**(尾部结构未闭合: 断在运算符/开括号/未闭合引号)被当作完整交付;下游"产物提取"表现为命中率抖动, 实为上游截断(真机: `completion=8192 上限, content=1209 字符, success=true`, 正文停在半行)。

- **验证判据**: 完整正文零误报(含全角标点结尾); 恰好一次续写(零额外成本路径必须 1 次调用); 续写为空 → 原文保留且仍可检出。

### 11-1 `policy-wiring-passthrough` —— 策略接线缺口（组件内实现正确 ≠ 主链生效）
- **前提**: 某项策略/能力实现在**消费方组件**内, 而决定其输入的参数由**上层调用方**提供。
- **失效机制**: 上层把该参数**硬编码为默认值**(或不传) → 消费方策略分支永远走默认路径, 实现沦为**死代码**; 更隐蔽的是消费方的**单元测试直接构造它并自己传参** → 全绿, 缺口被掩盖(真机实证: 首轮预算策略 12/12 单测通过, 主链首轮仍 `completion_tokens=8192`); 若没有"策略是否生效"的归因字段, 只能靠猜。
- **正确形态**: ① 参数必须**从真实上下文显式透传**(与既有同类透传保持同一模式); ② 至少一条测试**经由真实调用方**驱动(接线测试), 而非只测被调组件; ③ 策略生效与否落**可观测字段**(策略参数取值 + 触发它的分类标签), 使"没生效"能被直接看见。
- **验证判据**: 由真实入口驱动一次, 遥测中策略参数**非默认值**; RED 控制(恢复硬编码 → 接线测试必红)。
- **Instances**: `src/agent/modelqueue/ModelQueueAdapter.cs`(曾硬编码 `"general"`) + `src/agent/templates/IPromptBuilder.cs`(`Prompt.Intent`) + `src/agent/IndustrialAgentV2.cs`(透传); 机检 `FirstCallBudgetTests.真链适配器_意图透传_代码任务首轮即32768`。

### 11-2 `shared-output-budget` —— 共享输出预算（内部推理与交付物同池）
- **前提**: 同一次生成调用既产出**内部推理**又产出**面向用户的交付物**, 两者共用同一输出预算上限。
- **失效机制**: 内部推理体量不可控(真机 20k~28k 字符) → 吃满预算 → 交付物表现为**空**(预算全被推理吃掉)或**半截**(推理占大头, 交付物被切在半行); 两者**同源**, 若当两个独立缺陷分别修, 会反复(本轮真机: 3/3 轮触发恢复, 其中 2 轮空正文 1 轮截断)。
- **正确形态**: ① 首轮预算按**任务类型**给足(交付物体量上界 + 推理经验上界), 而非统一默认; ② "空正文/截断"恢复链只作**兜底**, 非常态路径; ③ 预算取值、命中策略与任务分类一并落遥测, 支持同题 A/B。
- **验证判据**: 同题 N 连跑, **首轮调用即完成**(恢复/续写次数=0)的比例上升; 单题 tokens 不因抬高上限而失控(上限≠实际消耗), 且有效产物率不降。

## 12. R374 新增教训实例（真机驱动, 通用化归档）

### 12-1 `failure-fact-reachability` —— 失败事实的**可达性**（"检测到失败" ≠ "失败可被消费"）
- **前提**: 某组件确实捕获了失败事实（错误文本 / 退出码 / 诊断输出），并已把它**写入自己的记录**(落盘/遥测/日志)。
- **失效机制**: 信息在**层层降维**中被剥离 —— 捕获层留下**全文**, 摘要层只留**状态**(一个退出码/布尔), 交付层只留**结论**。于是**观测面**完整(日志里能看到失败), **行动面**缺失: 需要依据失败内容**自我修复**的下游拿不到唯一输入（错误文本不在其上下文里）, 修复能力被**结构性掐断**, 且表现为"功能从未实现"而非"报错"→ 最难发现的一类缺口。判别陷阱: 测试若只断言"失败**被记录**"(绿), 永远测不出"失败**可被消费**"。
- **正确形态**: ① 从**最终消费方**反推可见性(模型上下文 / 用户可见面 / 自动化回路), 而不是从捕获点往下看; ② 摘要可以保留, 但必须**另有一条原始事实通道**(有界截断的原文尾段)直达消费方; ③"检测到失败"与"失败信息可行动"是两个断言, 分开登记。
- **验证判据**: **可见性断言**(下一轮输入中确实出现失败原文片段, 且与真实诊断一致) + **行动断言**(修复轮确实产生了**新的、通过复检的**产物); 负向控制: 关掉事实通道 → 用例必红。
- **Instances**: `src/agent/registry/PythonArtifactPlugin.cs`(此前仅把运行期 `stderr` 截 200 字进 `detail`、**stdout 整段丢弃**; 现补 `OutputExcerpt` + `ArtifactCheck.Output`) + `src/agent/registry/ArtifactRepair.cs`(`BuildPrompt` 回灌原文) + `src/agent/IndustrialAgentV2.cs`(接线); 真机 `/tmp/gameprobe/run_r374.sh`。

### 12-2 `repair-requires-new-artifact` —— "修复"必须由**新产物**定义（原地重试不算修复）
- **前提**: 对失败产物发起一轮自动修复, 修复后需要判定"是否修好"。
- **失效机制**: 判定若写成"复检时**存在任何一个通过校验的产物**", 则**同一产物的原地重跑**在非确定性场景(超时/环境抖动/资源竞争)下由失败变通过, 会被记为**修复成功** → 把**环境抖动**记成**模型功劳**, KPI 虚高且归因错误(与"必须带来源归因字段"同源风险)。
- **正确形态**: 复检判据 = **本次修复轮产出的、与失败产物不同(内容不同)的**新产物通过校验; 原地重跑变通过须**如实标注为"内容未变"**, 并把它与"修复成功"分开计数。
- **验证判据**: 构造非确定性用例(同一文件第二次运行即成功) → 修复判定必须为 **false**; RED 控制(把判据放宽为"任意通过产物" → 该用例必红)。
- **Instances**: `src/agent/registry/ArtifactRepair.cs`(`good = after.FirstOrDefault(a => a.Passed && a.Path != target.Path)`); 机检 `ArtifactRepairTests.同一文件重跑变通过_不算修复_必须由修复轮产出新产物`(RED-2 实测 1 红)。

## 13. R375 新增教训实例（真机驱动, 通用化归档）

> 同 §10 铁律: Id/前提/失效机制/验证判据**语言无关**; 具体文件与测试只进 `Instances`。

### 13-1 `channel-wired-is-not-channel-used` —— 通道接通 ≠ 生产侧命中（消费端就绪必须配生产侧触发率证据）
- **前提**: 某交互通道（问询/事件/推送/回血）的**消费端**已实现并接线（有实现者、有路由、有单测），且已具备“伪造输入能走通”的能力。
- **失效机制**: 消费端修好只解决“能力存在”，不解决“**是否被生产**”。若上游触发条件窄、或在特定分支被绕过，通道表现为**永不触发**——在观测上与“功能没实现”无法区分（都是零事件）。更糟的是**接线探针与单测都会绿**（伪造输入本来就能走通），于是产生“已交付”的假信号。
- **正确形态**: 三件套分开登记——① **契约**（形状/字段完备，机检）② **接线**（真机伪造输入能走通，真机级）③ **生产命中**（真实任务链路里确实产出该事件，真机 + 计数）。缺③时只能用“机制已通”措辞，**不得**写“管线会 X”。
- **验证判据**: 真机真实任务跑 N 次并统计事件计数；命中 0 时必须写明“触发条件未命中”并给出**生产者位置**（文件:行号），不得以接线证据代偿；负向控制: 把消费端摘掉 → 响应必须能区分（如 `channel_unavailable` vs `unknown_ask`），否则无法判定接线是否真在。
- **Instances**: `src/agent.frontendapi/FrontendPromptService.cs`（消费端）+ `src/agent.frontendapi/FrontendApiServer.cs` / `FrontendEventHub.cs`（接线）；生产者 `src/agent/IndustrialAgentV2.cs:1878`、`src/agent/registry/NodeExecutionResult.cs:332`；真机探针 `/tmp/fp375/probe.py`（P1 全绿 / P2 ask 事件 0）。

### 13-2 `framing-in-stream-protocol` —— 流式协议的帧边界必须显式（整块读取不得吞掉后续帧）
- **前提**: 长连接/管道协议，首帧做握手（鉴权/协商），随后是常规帧。
- **失效机制**: 握手按“一次读到多少算多少”整块消费首帧，则与首帧**同一批到达**的后续帧被静默丢弃 —— 客户端表现为**无响应/挂起**（不是报错），且只有在网络恰好分包时才偶发；流水线式客户端（写完 auth 立刻写首个请求）必然踩中，而“慢客户端”（人肉按回车）永远测不出来。
- **正确形态**: 任何按帧读取的入口都必须**返回未消费的残包**并交由下一次读取（或统一使用带缓冲的帧读取器）；握手只消费**首个分隔符之前**的字节，绝不整块吞掉。
- **验证判据**: 客户端把 auth 与首个请求**一次性写出**（同一 write / 同一 TCP 段）→ 首个请求必须得到响应；负向控制: 改回整块消费 → 该用例必红。
- **Instances**: `src/agent.frontendapi/FrontendApiServer.cs`（`TryAuthHandshakeAsync` 整块读）—— **R376 状态: 已修**（握手返回残包 Tail + 请求循环预置排空）；负向控制: 丢弃残包 → 2 用例红（已实证）；真机现象: `/tmp/fp375/probe.py` 首跑无响应、加 0.8s 间隔即通。


## 14. R376 新增教训实例（真机驱动, 通用化归档）

> 同 §10 铁律: Id/前提/失效机制/验证判据**语言无关**; 具体文件与测试只进 `Instances`。

### 14-1 `same-channel-inflight-starvation` —— 同通道回程饿死（读循环内等待长任务 → 对端答复永不被读）

- **前提**: 请求-响应与主动事件复用**同一条通道**；且请求的执行过程可能**内部发起子交互**（问询/回调/确认）并等待对端在该通道上回复。
- **失效机制**: 若"读循环"同步等待请求完成，则该请求正在等待的回复**只能由被占住的读循环读取** → 双向死锁，直到超时（症状是"卡住/无响应"，不是报错）。致命之处在于**测试若把子交互的触发源带外构造**（直接调用内部方法），读循环空闲 → 单测全绿、接线探针也全绿，只在真实入口触发时死锁。
- **正确形态**: ① 读循环只做**解析 + 派发**，长任务并发执行；② 并发**有界**（在途上限 = 背压）；③ 异常**必被观测**（不静默吞）；④ 发送面**共用一把锁**（行不交错）；⑤ 连接断开时给在途任务**有界收尾**（不得无限等待）。
- **验证判据**: ① 一条测试**经生产入口**发起长任务（触发源不在测试里直接构造），并在同通道回发答复 → 长任务必须继续完成并产出正文；② 长任务在途时再发同通道其它请求 → 必须**及时**得到响应（不等长任务）；③ 负向控制: 把读循环改回同步等待 → 上述两条**必须变红**，而带外构造的旧式用例仍绿（把盲区本身也变成证据）。
- **Instances**: `src/agent.frontendapi/FrontendApiServer.cs`（读循环/`Dispatch`）；回程路径 `FrontendApiChatRouter.cs`(`ask.reply`) + `FrontendEventHub.cs`；生产者 `src/agent/registry/EvidenceGate.cs` + `src/agent/IndustrialAgentV2.cs`；真机探针 `/tmp/fp376/probe2.py`（3/3 闭环）。

### 14-2 `multiplexed-channel-ordering-contract` —— 复用通道的顺序契约必须显式（事件与响应相对顺序不保证）

- **前提**: 同一通道复用多类消息（响应 + 主动事件 + 子交互消息），且实现由"串行处理"演进为"并发派发/独立回程"。
- **失效机制**: 并发化后**事件可能先于其触发的响应到达**；测试若在"读响应时丢弃途中无关消息"或"按到达顺序断言"，会得到**假红**（被误判为产品缺陷）或**假绿**（恰好顺序正确）。契约不写清时，客户端实现也会各自假设顺序。
- **正确形态**: 契约显式声明"响应按**标识**关联、不保证到达顺序"；测试**暂存**无关消息而非丢弃，断言顺序无关；仅在语义确有顺序要求处才额外断言顺序。
- **验证判据**: 断言在任意到达顺序下稳定通过（复跑 N 次不抖动）；顺序敏感之处必须能给出**到达顺序**的实测记录，否则只能写"不保证顺序"。
- **Instances**: `src/agent.frontendapi/FrontendApiServer.cs`（并发派发）+ `src/agent.tests/FrontendAskFlowTests.cs`（读取暂存不丢）；触发症状（R376 机检, 未逐帧记录顺序故不断言具体先后）: `ask.cancel` 场景中断言先读响应、途中到达的 `ask_closed` 事件被丢弃 → 后续事件断言读到超时（8s）而红；契约定为顺序无关后稳定绿。


## 15. R377 新增教训实例（真机/负向控制驱动, 通用化归档）

> 同 §10 铁律: Id/前提/失效机制/验证判据**语言无关**; 具体文件与测试只进 `Instances`。

### 15-1 `helper-called-is-not-wired` —— 「调用了辅助」不等于「值真的进了产物」（接线断言的空心陷阱）

- **前提**: 为实现某个 KPI/指标，引入一个纯计算辅助（口径、换算、格式化），由若干打点/产出点调用它。
- **失效机制**: 若断言只数「辅助被调用的次数」或「辅助本身算得对」，则**"算了但没铺进产物"**这一半断链完全测不出——
  计算行存在、辅助调用计数正确、单测全绿，而产物字段里根本没有该值（或只有部分路径有）。负向控制一旦真删掉铺设动作，断言照样绿 = **空心判定**。
- **正确形态**: 接线断言必须**绑定"值出现在对外产物的字段里"**，按**产出点逐块配对**（每块都含该值的铺设），而不是全局计数；
  计数相等只能作为附加提示，不能单独承担接线证明。
- **验证判据**: 反向注入「删掉任意一处铺设」→ 断言**必须变红**（逐点验证，不是抽样一处）；若某次注入没红，先判定是断言空心，再谈实现。
- **Instances**: `src/agent.modelqueue/ModelQueueRouter.cs`（三处 `llm_call` 打点）+ `src/agent.tests/PromptCacheKpiTests.cs`（按打点块配对；R377 变异③首跑 0 红 → 修正后 1 红）。

### 15-2 `absent-is-not-zero` —— 「缺失/未上报」必须与「零值」区分（否则没测到会被读成指标为 0）

- **前提**: 指标来自外部提供方（API/采集器/第三方），可选项在部分来源上不被上报。
- **失效机制**: 用 `0` 兜底缺失值 → 聚合时"没测到"与"实测为 0"混为一谈，比率被系统性拉低（或拉高），
  且**看板上无法分辨**：一个 0% 的指标到底是真差还是没数据。反之把 0 记成"未上报"则会掩盖真实的坏结果。
- **正确形态**: 缺失用**显式哨兵**（如 -1 / null）表达，聚合时**单独计数**并排除在比率分母之外；只在**有真实分母**时才算比率；
  打点里两种语义必须是两个不同取值，且聚合脚本要能分别打印「上报 N/M 次」。
- **验证判据**: 构造"全缺失""真 0""部分缺失"三类输入 → 输出必须分别是哨兵 / 0 / 仅按上报子集计算；任一混淆即红。
- **Instances**: `src/agent.modelqueue/PromptCacheKpi.cs`（`Unknown=-1`，`HitRate` 无分母 → -1）+ `scripts/kpi_cache_hit.py`（上报 4/45 与 41 次未上报分列）+ `src/agent.tests/PromptCacheKpiTests.cs`。

## 10. 新教训落库 (R380 真机暴露 · 通用化后)

> 口径: `Id`/`Pattern`/`Precondition`/`Mechanism`/`Verify` **零语言特性**(语言/工具名只允许出现在 `Instances[]`), 满足 §4-7 / A8 机检。

### 10.1 等待式失败放大器

| 字段 | 内容 |
|---|---|
| Id | `fnv1a32(kind+pattern)` — 见 `LessonTable` 计算, 不入档 |
| Kind | Failure |
| Pattern | **前置条件缺失时"等待"而非"验证" → 失败成本由毫秒放大到超时上限** |
| Precondition | 组件依赖外部资源(子进程/端口/文件/凭据), 且该资源的"存在性/就绪性"未被使用前校验 |
| Mechanism | 资源缺失 → 依赖进程立即退出 → 等待方只轮询"是否就绪", 不检查"是否已死" → 只能等到超时上限才报错; 期间占用排他锁/配额/调度槽位, 并把失败从"可立即修复"变成"每次调度白烧一个超时周期" |
| Verify | ① 缺失资源场景下失败耗时 ≤1s (真机: 修复前 900s → 修复后 0.000s); ② 依赖进程退出即中断等待并回吐其日志尾; ③ 使用前校验存在性, 缺失即记录并跳过(不进入等待) |
| Instances | llama-server 模型文件缺失(900s 死等) |
| Scope | 通用工程(子进程/端口/服务/凭据/挂载点) |

### 10.2 同构多表示的形状静默错

| 字段 | 内容 |
|---|---|
| Id | `fnv1a32(kind+pattern)` — 见 `LessonTable` 计算, 不入档 |
| Kind | Failure |
| Pattern | **同一矩阵/张量的两种等价表示(嵌套行 vs 扁平行主序)只有一个生产者时不暴露; 第二个生产者接入即静默算错或崩溃** |
| Precondition | 跨模块传递定长数组(矩阵/张量), 且消费方对"行主序/嵌套"只做隐式假设, 无形状断言 |
| Mechanism | 旧生产者恰好产出消费方预期的形状 → 长期无异常; 新生产者产出另一种等价形状 → 消费方按错误步长切片: 要么抛类型错(可见), 要么**静默算出错误的数值结果**(更危险); 序列化路径(落盘/加载)与内存路径若形状不一致, 缺陷只在"新生产者 + 落盘"组合下出现 |
| Verify | ① 两种形状输入必须给出**逐元素相同**结果(回归用例); ② 构造入口对形状**归一 + 断言**(拒绝第三种形状); ③ 负向控制: 错形状必须被断言拦住而非静默算出垃圾 |
| Instances | 嵌套行 W(回归求解产出) vs `matvec`/序列化假设的扁平行主序 |
| Scope | 通用工程(任何跨模块传递定长数组/张量的场景) |

**落地位置**: `eval/bge/test_adapter_shape.py` (实例回归: 嵌套==扁平 + 负向控制); 通用判据 **A8 黑名单机检**覆盖本节 Id/Pattern。
