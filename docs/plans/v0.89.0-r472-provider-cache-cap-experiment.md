# v0.89.0 / R472 计划 —— 远端前缀缓存「饱和」成因判定: 供应商硬上限 vs 共享前缀长度 (真机受控实验)

> 本轮定位:**前提裁决轮**。不新增产品功能, 只裁决 R469/R470/R471 三连结论所依赖、且从未被测量过的一个前提。

## 1. 为什么是这个靶点

| 轮次 | 依赖的未验证前提 | 若前提为假会发生什么 |
|---|---|---|
| R469 | 命中率 = 分档上限 `P/(P+用户轮)` ⇒ 97% 单值红线对长轮「结构性不可达」 | 该「不可达」是采样/假设产物, 红线口径须重写 |
| R470 | 真实流命中 ≤ 2,304 视作上限, 据此把 `shared_prefix` 通道定义为跨会话复用 | 通道语义与基线(miss 59,518)建立在错机制上 |
| R471 | 把 43 条派生值当优化基线 | 优化方向可能指向无收益处(升前缀 >2.3k) |

两个互斥假设:
- **H_cap(供应商硬上限)**: 命中量在 ~2,048–2,304 处被 provider 截断 ⇒ 把稳定内容前置到 2.3k 以上**零收益**, 主线唯一杠杆 = 压「每次实际发送的内容」(历史/注入)。
- **H_prefix(共享前缀长度)**: 命中量 = 与历史调用共享的前缀长度(块对齐) ⇒ **升前缀有余量**, R469 式须重写。

先裁决前提再做实现, 避免在假前提上继续堆代码。

## 3. 设计

真机受控实验(8 次调用, 单模型单端点), 不碰产品链:

```
共享前缀阶梯(每臂 system 消息字节完全一致):  SMALL ~0.9k tok | MID ~3.8k tok | BIG ~5.8k tok
每臂: cold(唯一 nonce 开头, 无任何共享前缀) → warm(同前缀 + 不同 user)
外加: BIG.warm2(第二复现) + BIG.ident(与 BIG.warm 完全同文)
```

- 读回: `prompt_tokens` / `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 逐调用落盘。
- 判别: 命中随前缀增长 ⇒ NO_CAP; 命中在前缀增长 1.5× 后不涨 ⇒ CAP。
- 预注册判据 C1–C7 先落盘(`eval/rover/r472/prereg-r472.json`, mtime 早于首次调用), 阈值 0.85 / 0.65 **不得事后调整**。

## 4. 约束

1. **凭据卫生**: key 只从 `.env.local` 读入进程, 不打印、不落盘、不入 git config; 证据只留 usage 数值 + 请求体 sha256。
2. **成本硬上限**: 预注册 < 60,000 prompt token(< 0.02 CNY)。实测 32,643 + 128 completion = **0.008954 CNY**。
3. **判据纪律**: 预注册判据被证伪 ⇒ 宣称必须收窄, 事后修正单列 `posthoc`(本轮 C7 自检失败即按此路径处理, 不覆盖原判)。
4. 本轮无 C# 改动 ⇒ 按铁律**不触发** AOT 重发布(铁律约束的是改链代码后的重发布, 此处为「不触发」而非「未测到」)。
5. 禁 push(`.git/PUSH_PAUSED` 在位), commit 仅本地。
