## 二、标准工业模式 (对标: LLM 应用上下文管理的通用做法)
| 模式 | 说明 | 本框架映射 |
|---|---|---|
| **M1 分级降级链** (graceful degradation): 压缩失败 → 次级压缩 → 原文截断 → 拒绝注入 | 每级都可用, 不炸主链 | G1/G4 → DefenseChain |
| **M2 原文不可变源** (immutable source of truth): 压缩产物可随时从原文重建, 原文永不覆盖 | 恢复性 | G3 → 原文快照落盘 (原文是 RAG 源文档, 本来就在) |
| **M3 关键信息白名单** (critical-token preservation): 数字/日期/实体/指令词压缩前提取, 产物缺失即判失败 | 精准校验 (semantic 盲区补丁) | G2 → 已有 ground-truth 方法论 (audit) 迁移到运行时 |
| **M4 熔断器** (circuit breaker): 连续 N 次压缩失败 → 熔断压缩 (直通原文) + 告警, 半开恢复 | 防止系统性失灵时反复硬跑 | G4 |
| **M5 审计采样** (continuous audit): 线上抽样比对压缩产物 vs 原文关键信息 | 我们已有 audit 体系 | 定期化已入 §0-2 |
| **M6 配额硬顶** (token budget cap): 压缩后仍超配额 → 按重要性排序截断, 不无限回退 | 防"宁大不歪"变成"无限膨胀" | 已有 allocation, 需回退路径再校验 |

## 三、实施方案 (G1-G5 → M1-M6)
### D1 异常隔离 (G1→M1)
- CompressSnippetsAsync 内 per-snippet try/catch: 压缩异常 → 该 snippet 回退原文 + 打点 `compression_error` (ex_type, msg≤80ch); 单条异常不再炸整轮。
### D2 关键信息哨兵 (G2→M3)
- 压缩前提取哨兵 token: 数字串 (≥3 位)、日期模式、SN-/编号、引号内实体;
- 产物缺失任一哨兵 → 判失败 → 逐级回退 (SummarySentences 失败 → RuleCompress → 原文);
- 打点 `compression_sentinel` (lost_n, samples≤5)。
### D3 降级链 (G1→M1)
- SummarySentences → (失败) RuleCompress → (失败) 原文截断至配额 (M6: 尾部截断, 关键句保护评分复用) → (仍超) 拒绝注入该 snippet 并告警。
### D4 熔断器 (G4→M4)
- 连续 5 次压缩失败 (异常或哨兵丢失) → 熔断 60s (直通原文) + 打点 `compression_breaker` (state=open);
- 半开: 60s 后放行 1 条试压缩, 成功 → closed。
### D5 原文恢复源声明 (G3→M2)
- 文档化: RAG 源文档 = 不可变原文源 (本就落盘 index.jsonl); 压缩产物只在 prompt 组装层, 不落盘不覆盖 — 架构上已满足, 补声明 + 恢复路径测试 (GetAsync(id) 取原文)。

## 四、验收
- 单测: D1 异常注入 (compressor 抛异常 → 回退原文不炸) / D2 哨兵丢失回退链 / D4 熔断开合;
- audit 复测: 104 篇多样态 + 哨兵启用后 keys/causal/instr 保持 ≥95%;
- 打点: compression_error / compression_sentinel / compression_breaker 进 ledger。
