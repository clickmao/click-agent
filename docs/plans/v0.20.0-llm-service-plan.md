# v0.20.0 LLM 服务独立进程计划 (R342 立项 — 用户钦定 2026-09-10；R343 manager 架构定稿)

> 用户指令: "将llm服务写成单独进程, 以免新CLI重新加载LLM到显存内, 最好使用小而完善的框架完成"
> R343 用户钦定策略: "一个是 llm-manager 进程, 一个是实际 llm-service-host; **卸载直接杀 llm-service-host 就好了**"

## 0. 现状事实 (证据)

- BgeEmbedder (src/agent/llamalocal/BgeEmbedder.cs): LLamaSharp LLamaEmbedder 惰性加载 bge-q8.gguf (26MB 权重, 加载后 RSS ~157MB 实测), 每 CLI 进程经 DI 新建 → 每次启动重载
- 进程内共享 SharedEmbedderRegistry (vectormemory, T-B) 只解决同进程双链重复, **不跨进程, 且无卸载 API**
- LLamaSharp 事实: `LLamaEmbedder.Dispose()` 只释放 Context, **不释放 _weights**(native 模型内存); 手工卸载需穿透注册表+引用计数 → 复杂易漏
- CLI 生命周期事实 (Program.cs): 交互 REPL (`while(true)` L296, EOF//exit/Ctrl+C 结束) 或 one-shot (-q); 任务边界=每次输入一个回合; 多实例并存 → 模型随进程反复加载
- 通道设施: agent.io SharedMemoryChannel 单向(agent→前端) — 不适合双向 RPC

## 1. 范围纪律 (用户纠正, 逐字)

> "本机llm服务与cli本机利用高速通道通讯 【注意】仅是新增本机llm host 而非全面修改当前框架llm使用流程"

- ✅ 新增: llm-manager daemon + worker host + 客户端 RemoteEmbedder (显式选用)
- ❌ 不改: DI 注册/BgeEmbedder 进程内路径/现有 LLM 调用流程 — 原样保留, 可回退
- 高速通道: Unix Domain Socket (BCL; 比 TCP loopback 低延迟; Windows 10+ AF_UNIX 支持)
- 跨平台铁律 (用户 OOB): **产品代码零 shell** — `Process.Start`+`ArgumentList` spawn; `Process.Kill(entireProcessTree)` 卸载; daemon 自写日志 (env LOG) 不依赖 sh 重定向

## 2. 架构 (R343 定稿 — 用户钦定策略)

```
CLI(s) ──UDS(client sock)──→ llm-manager (轻量常驻, 0 模型, 不随 CLI 生死)
                                ├─ lazy:    首个使用请求 → spawn worker
                                ├─ supervise: worker 崩溃/被杀 → 下次请求重拉 (客户端无感)
                                ├─ unload:  资源紧张 ∧ 无 CLI 实例 ∧ 无进行中请求 → kill worker
                                └──UDS(worker sock)──→ llm-service-host (真 bge, 可被杀)
```

- **卸载 = 直接杀 worker 进程** (用户策略): OS 回收全部 native 内存 — 绕开 LLamaSharp weights/context 手工释放与引用计数; worker 重启成本 = 模型加载 (lazy 触发时付一次)
- manager 透明代理: 客户端协议不变 (行 JSON: `{"op":"embed","text":...}` / `ping`)
- **ping 由 manager 直接应答** (探活不触发 worker 加载 — lazy 语义)
- 双启保护: manager pid 文件 (`.manager.pid`); worker pid (`.worker.pid`) 由 worker 自写
- **孤儿清理**: manager 被 SIGKILL (无 Dispose) → worker 成孤儿; 新 manager Start 时读 `.worker.pid` 杀掉孤儿 (否则误复用/占内存)

## 3. 崩溃/卸载机制 (用户三问 + 资源策略)

### 3.1 两个 CLI 同时启动?
- 客户端抢占 `.startlock` (`FileMode.CreateNew` 原子) — 抢到者 spawn manager, 抢不到者等 READY 复用
- manager 内 lazy spawn 由 `SemaphoreSlim(1)` 串行 (并发请求只 spawn 一次 worker)
- daemon 双启保护: 构造时 pid 存活 → 抛 (拒绝第二实例)

### 3.2 中途 worker 崩溃?
- manager 转发前 `ProbeWorker()` → 失败则重拉 (带 45s 就绪预算); 客户端侧 3 次退避重连
- 真机验证: kill -9 worker → 下次请求新 worker pid ≠ 旧 pid, 客户端结果正确

### 3.3 内存/显存崩?
- **卸载判定 (纯函数, 单测覆盖)**: `ShouldUnload(availMb, floorMb, cliCount, inflight, workerUp)`
  = `workerUp ∧ inflight==0 ∧ availMb>0 ∧ availMb<floorMb ∧ cliCount==0`
- **不按时间** (用户钦定): 内存充足就常驻; 仅资源紧张 ∧ 无 CLI 实例时卸载
- 空闲长连接**不**阻止卸载 (CLI 保持 socket 但无请求 ≠ 在用)
- 熔断: 客户端侧窗口 5min 内 spawn ≥3 次 → 拒自启 (防重启风暴)
- 读不到内存 (非 Linux/异常) → 保守不卸载 (优雅降级)
- env 可调: `AGENTFRAMEWORK_LLM_SERVICE_MEM_FLOOR_MB` (默认 512) / `AGENTFRAMEWORK_LLM_SERVICE_UNLOAD_CHECK_MS` (默认 15000)
