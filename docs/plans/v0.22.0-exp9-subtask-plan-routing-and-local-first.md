## 0. 目的（先定目标函数，防"为编排而编排"）

**唯一目的 = 三 KPI**（不达标即回退此计划）：

| 指标 | 现状 | 目标 |
|---|---|---|
| ① tokens | 一切（含本地可完成的工作）都走一次 LLM 单轮 | 本地可完成的节点 **零 LLM 调用 / 零 token** |
| ② 端到端耗时 | 远程生成期间本地空等（全串行） | 无依赖的本地下游节点在远程 in-flight 期间**先跑**（真并行） |
| ③ 前端可见性 | 前端 API 无步骤/计划通道，用户只见最终回复 | 每节点 **location(本地/远程)/state/依赖/产物/耗时/tokens** 可推送可查 |

**反向约束（用户钦定）**: 新增结构若不能在上述三项上被测量到改善，即视为"编排表演"，不得合入。

## 2. 根因（按失败模式表归类）

| # | 类别 | 说明 |
|---|---|---|
| R1 | **断链**（头号失败模式） | 组件（拆解/计划/引擎/本地执行体）全部存在且单测绿，**调用方没接**：主链注入哑执行体 → "策略永不触发" |
| R2 | **缺维度** | 本地/远程路由不是实现遗漏，而是**从未建模**（模型无字段、Builder 无判定）→ 前端即使想画也无数据 |
| R3 | **归属错位** | 本地执行能力挂在"LLM 单轮输出**之后**的产物闸门"，没有挂到"计划节点**之前/之中**"→ 结构上不可能"先本地做" |
| R4 | **通道缺失** | 前端 API 只有 ask/reply + 通用 envelope；计划/节点状态无事件 |
| R5 | **KPI 盲区** | `loop_turn`（`IndustrialAgentV2.cs:1555-1558`）不带计划/产物结论 → 本地省了多少 token、并行省了多少秒，一律不可测 |

## 3. 设计（最小真闭环；每项都必须能被 KPI 或前端观察到）

### D1 计划节点增执行位置（数据模型）
`PlanNode` 新增（AOT 纯数据字段，走 `TaskPlanJsonContext` source-gen）：
- `ExecutionLocation Location` ∈ `{ Local, Remote, Hybrid }`
- `string? LocalExecutorId`（如 `python.run` / `skill.script` / `isolate.task` / `text.process`）
- `string? LocalHint`（判定依据短句，供前端显示"为什么这步可以本地跑"）

### D2 判定规则 = **确定性表**，不是 LLM（关键：不得让 LLM 拍脑袋分类）
来源 = 既有能力事实：
1. 本地有能力执行器（`LocalExecutorRegistry`，登记 `python.run`/`skill.script`/`isolate.task`/`text.process`/`file.op`…），且
2. 任务类型映射命中（代码产物/文本处理/文件操作/状态反核 = 可本地；纯推理/创作/信息检索 = 远程），且
3. 节点参数齐备（`IsExecutable`）且无敏感/凭据依赖
→ 三条全真 = `Local`；需要生成新内容 = `Remote`；两者兼有 = `Hybrid`（远程生成 → 本地跑/验，正是用户原话场景）。
**负向控制**：映射未命中或本地执行器缺失 → 必须落 `Remote`（不得乐观判 Local）。

### D3 真执行体注入（替换哑体）
主链注入真 `nodeRunner`：
- `Local` → 本地执行器（`PythonRunVerifier`/`ScriptPluginRunner`/`IsolatedTaskRunner`），**零 LLM 调用**，产物落 `data/artifacts/` 并复用现有台账/闸门
- `Remote` → `ModelQueueRouter`（token/缓存 KPI 复用现有打点）
- `Hybrid` → Remote 生成 → 立即本地执行/校验（复用 `ArtifactRepairLoop` 语义，但**由节点驱动**而非整轮驱动）
- 关闭开关：env `AGENTFRAMEWORK_PLAN_EXEC`（默认开；=0 回退哑体，保留旧行为可比对）

### D4 本地先行（真并行，用户的"等待期先跑起来"）
- 已有 `TaskPlan.ExecutableNodeIds` + `MaxParallelism` 作为调度入口
- 规则：远程节点发起后**不阻塞**，同层（`ParallelGroup` 相同 / `Level` 相同）无依赖的 `Local` 节点**立即执行**；本地完成后若命中远程节点的前序产出依赖才阻塞等待
- 并发上限：`MaxParallelism`（默认 4）+ 本机 2 vCPU 实际钳制（`Environment.ProcessorCount`），防 CPU 打满拖慢远程回程解析

### D5 前端可见（用户原话的"给到前端API显示"）
- `FrontendEventHub` 增事件（复用 `EmitAsync` envelope，AOT source-gen 序列化）：
  `plan.created`（节点树：id/text/intent/location/executorId/dependsOn/level/parallelGroup）
  `plan.node`（state: Pending→Running→Completed/Failed/Skipped；耗时 ms；tokens；产物路径）
  `plan.finished`（总耗时、本地节点数、远程节点数、**本地节省 token 估算**）
- `/plan` 保留（拉取式兼容）；事件为推送式，前端可只订阅

### D6 KPI 打点（否则无法证明不是编排表演）
- 新点位 `plan`（节点数/本地数/远程数/并行组数）+ `plan_node`（id/location/executor/state/ms/tokens/artifact）
- 验收对照：**同题**（PY 开发小游戏）优化前后 —— ① LLM 调用次数 ② tokens ③ 端到端 ms ④ 前端可见节点数

## 4. 约束（违反即返工）
1. **不为编排而编排**：每项改动必须能落到 D6 的四项对照数字上。
2. **零反射 / AOT 可用**：计划与事件序列化走 source-gen（`TaskPlanJsonContext` 同族）；不引入动态类型。
3. **跨平台零 shell**：本地执行一律 `ProcessStartInfo.ArgumentList` 直连（沿用 `PythonRunVerifier` 既有做法）；tmux/真机按键属**探针层**，不进产品路径。
4. **确定性判据**：D2 判定为纯函数，可单测；与提示词注入（`SessionBaseline`）**同源**，防"提示词与闸门漂移"。
5. **诚实边界**：本地执行失败不得静默降级成"远程重做"来掩盖；节点失败如实标 `Failed` 并保留产物。
6. **门禁**：新增能力必须有"消费方断言"测试（防再现 R1 断链）；无消费方 = 不合并。

## 5. 验收（真机）
1. **单测**：D2 判定矩阵（Local/Remote/Hybrid 各正例 + 负向控制）；D3 执行体注入后"哑体不再被使用"的反向断言；D4 并行序（本地节点在远程节点完成前已 Running/Completed）。
2. **真机 A（PY 开发小游戏，同题对照）**：`plan.created` 事件含 `location` 字段；`plan_node` 里出现**至少一个 Local 节点在 Remote 节点之前/并行完成**；tokens 与 LLM 调用数 **不高于**优化前同题。
3. **真机 B（文本处理类）**：远程生成 → 本地立即跑（`script_run` 出现在远程调用之后但**不新增 LLM 调用**）。
4. **前端**：订阅事件可见节点树（location 标注"本地/远程"），节点状态实时变化。
5. **AOT**：发布 tag 轮校验 0 IL 警告（登记口径 `aot_check_policy=release_tag_only`）。

## 6. 排除项（本轮不做）
- 不做分布式/多机调度（本机单机场景）。
- 不做"计划可视化 UI"（前端实现方负责，本仓库只暴露事件与字段）。
- 不做 MCP / 外部生态接入（既有立场不变）。
- 不重写 `IntentDecomposer` 拆解质量（本轮只做"路由 + 真实执行 + 可见性"）。

## 10. D4b 出站扣减（实施：修 §9.5-2 的重复计算）

**问题**（真机实测）：路由判了"这活儿本地干"，但**原文照发**给模型 ⇒ 模型把同一步又算一遍（模型报 118 / 框架算 117），零 token 收益被拆解粒度吃掉，用户看到的还是模型那个数。

**设计原则**：**路由是"谁来做"，不是"记账"** —— 已判 Local 的子请求**不许再发给模型**；它的结论必须由框架补进答复，否则就是"删了用户的诉求"。

**三条判据（全部确定性，无 LLM 参与）**

| 层 | 判据 | 位置 |
|---|---|---|
| 节点级 | `DependsOn` 空 ∧ `AsksSourceTextOp`(动作词∧原文对象词) ∧ 非产物型 ∧ ≤60 字 ⇒ `Local(text.process)` + `IsLocalizedRequest=true` | `PlanRoutePolicy` R2c |
| 片段级 | 片段在原文**唯一**定位 + 向左吸收连接词/边界 + 向右吸收边界 + 相邻区间**合并** + 剩余 ≥25% | `RequestAblation.Subtract` |
| 计划级 | 仅当计划**仍有远程节点**承担请求时才扣减（全本地 = 本地独占回合 D4c，本轮不实现） | `RequestAblation.SubtractForPlan` |

**保守方向（宁可不扣，绝不改坏用户原话）**：片段定位失败 / 出现多次 / 剩余不足 25% / 全本地 / 无可扣 → **一律不扣**，逐字原文出站，并记 `abort_reason`。

**答复闭环**：扣减掉的子请求由框架自渲染（`PlanLocalAnswer.Render`）—— 成功 `请求 ⇒ 本地结果`；失败 `请求 ⇒ (本地执行失败: …)`，**失败也要说出来，不许静默**。

**留痕**：遥测 `plan_ablate`(applied/removed_chars/clauses/reason/src_chars/out_chars) 与 `plan_local_answer`(items/chars/ok)；`PlanNode.IsLocalizedRequest` 上前端。

**机检**：`PlanAblationTests` 24 例，含反向控制 —— 代码类子请求不本地化、有依赖不本地化、长句不本地化、片段多处不扣、剩余不足不扣、全本地不扣。

## 11. T4 决策：真跑闸门的默认值 + "测试用 py tool"

**决策（本轮钦定）**：`AGENTFRAMEWORK_PY_RUN` 未显式设置时，默认值 = **本机是否已装固定解释器**（`PythonInterpreterResolver.HasPinnedInterpreter()`）。

**理由**：产物自测（`--selftest`）必须真跑才有物理含义；但"真跑"要有**可复现的解释器**。若只有 PATH 上恰好存在的 python，则"跑过了"不可复现 —— **不可复现的通过比不通过更危险**，故只有 `explicit/pinned/managed` 才默认真跑，仅 `path` 兜底时保持默认不跑。

**解析顺序**（单一事实源 `PythonInterpreterResolver`，纯函数可注入可单测）：
① 显式 `AGENTFRAMEWORK_PY_EXE`（兼容旧名 `AGENTFRAMEWORK_PYTHON`）→ ② 仓库固定记录 `tools/py/interpreter.txt` → ③ uv 托管解释器目录（版本降序）→ ④ PATH。返回 `(Exe, Source)`，来源随结果走。

**py tool 下载**：`scripts/fetch-py-tool.sh` —— `uv python install cpython-3.12.14`（uv 自带下载校验）→ 写 `tools/py/interpreter.txt`（本机产物，`.gitignore` 掉）。

**显式值语义（fail-safe）**：`1/true/on/yes` = 开，**无条件**；`0/false/off/no/其它非空值` = 关；只有**空值**才走上面的默认。

**硬化**：闸门只对 `.py` 产物开放（非 python 产物不进这条执行路径）；解释器来源进 `PythonRunResult.Interpreter` 与 `script_run.interp` 遥测（**"跑过了"必须能对账是跑在哪个解释器上**）。

**诚实边界**：无沙箱、无 seccomp，以当前进程用户权限运行 —— 本决策解决的是"解释器可复现"，**不解决**"恶意产物"。

**机检**：`PythonInterpreterResolverTests` 9 例：解析顺序（用注入假 FS，不依赖本机布局）、记录文件失效回退、全无 → null（不瞎猜路径）、PATH 兜底标注 `path`、闸门语义表、非 `.py` 拒绝、**真 spawn 校验退出码**、失败退出码透传。

## 12. D7 运行时依赖等待（用户新增测试点；设计定稿，实施见 §12.5）

**场景（用户原话）**：A、B 并发启动；A **跑到中途**才发现要用 B 的产出数据，而 B 正在问用户、用户还没回复（或 B 尚未产出）⇒ **A 必须等 B 产出该数据后才继续**。

逐问题回答：

| # | 问题 | 结论 |
|---|---|---|
| 1 | 依赖是声明时还是运行时？ | 运行时（晚绑定）。`DependsOn` 是建计划时的声明；D7 补"执行中发现"的依赖 |
| 2 | 怎么发现？ | **确定性判据**：节点输入解析时命中"引用另一节点产出"（`$node:<id>` 或指名另一节点）→ 判定为运行时依赖；不许 LLM 拍脑袋 |
| 3 | B 未产出时 A 做什么？ | 进 `Waiting` 状态 + `wait_for=<id>` + `reason∈{running,user}`；**不消费输入、不伪造、不静默降级** |
| 4 | B 在等用户呢？ | A 保持 `Waiting` 跨轮；用户下一轮回复 → B 完成 → 唤醒 A 继续（需计划状态跨轮保持 + 唤醒入口） |
| 5 | 死锁/永久等待？ | 等待图**无环校验** + 有界超时 + 终态 `Blocked`（诚实报告，不许 hang） |
| 6 | 怎么看见？ | `plan.node` 事件带 `state=waiting`/`wait_for`/`wait_us`；前端可见；KPI 记等待时长 |
| 7 | 安全？ | 等待不引入新执行权限；超时/中断复用同一条 kill 路径 |

**验收（真机）**：① A 中途等 B 的产出（状态序列 `running→waiting→completed`，消费到的是 B 的**真实产出**，非替代文本）；② B 等用户 → A `waiting` 跨轮 → 用户回复后 A 完成；③ 负向：B 失败 ⇒ A **失败不静默**；④ 死锁用例被拒。

**待确认 T5**：A 等待期间是否占用并发额度（倾向：**不占**，让其它可跑节点继续）。→ **已决：不占**（见 §12.5 实现：等待 = 延迟队列，不持并发额度；额度=1 时也不死锁，`等待不占并发额度_额度为1也不死锁` 真断言）。

### 12.5 D7 实施记录（本轮交付）

**改动**：`TaskPlanRun.cs`（`PlanNodeState.Waiting` / `TaskPlanRunState.PausedForDependency` / `NodeWaitRecord` / `run.Waits` / KPI `WaitNodes,WaitUs` / `NodeOutcome.WaitFor,WaitReason`）、`TaskPlan.cs`（`PlanNode.RuntimeDeps`）、**新建** `RuntimeDependencyScanner.cs`、`NodeExecutionResult.cs`（`NeedNodeId` + 延迟队列/唤醒轮次/成环与超限与终止收敛）、`PlanRunner.cs`（`ResolveInput` 运行时依赖优先、等待事件出口 `EmitWaitAsync`、`plan.node` 载荷加 `wait_for/wait_reason`、KPI 汇总）、**新建** `PlanRuntimeWaitTests.cs`(11 例)。

**语义要点**
1. **发现路径两条**：① 执行前按显式契约预判（`$node:<id>`/`$dep:<id>`/`<id>的产出`，确定性扫描，不猜自然语言）；② 执行**中途**由执行体返回 `FinalState=Waiting + NeedNodeId`。
2. **等待不占额度**（T5 已决）：等待 = 延迟队列（本层不跑、不持并发额度），层批结束后由**唤醒轮次**重跑；并发额度=1 亦不死锁。
3. **唤醒**：生产节点落终态 → 注入 `RuntimeDeps` → **重跑**消费节点（`TextProcessExecutor.ResolveInput` 运行时依赖优先，拿到的是生产节点的**真实产出**）。
4. **有界等待**：默认 600s；**先判上限**（含"产出迟到"）⇒ 超限如实失败、不采用迟到产出（顺序错了 = 假的边界，机检 `等待超上限_如实失败`）。
5. **死锁在记账时拒**：等待图无环校验（含自环），不靠超时发现。
6. **生产节点在等用户** ⇒ 消费节点 `Waiting(reason=user)` + 计划 `PausedForDependency`（本轮不产出、不伪造）。
7. **提前终止收敛**：FailFast/Cancelled 时等待中的节点明确落 `Failed`/`Skipped`，**不留悬空 Waiting**。
8. **可见性**：`plan.node{state:"Waiting", wait_for, wait_reason}` + `plan_wait` 遥测 + KPI `WaitNodes/WaitUs`。
