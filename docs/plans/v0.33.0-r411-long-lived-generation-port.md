# v0.33.0 · R411 —— 长驻生成端口 + 本地 K2b 台账（补 R410 缺的「长驻」一环，并钉死本地缓存口径）

状态: 已实施（R411，2026-09-14）

## 0. 问题拆解（先确认问题本身）

R410 把 K2b 从「推断」变「实测」，结论是三条件：**长驻进程 + 稳定长前缀 + cache 开**；并测出产品通路缺口 —— 每次调用新起 server ⇒ `cached=0`。R411 问的因此不是「能不能复用」，而是三件更具体的事：

1. **接线**：把「长驻」做成产品侧可复用端口（本进程内一个 server 跨轮保活），而不是只在探针里成立；
2. **口径**：本地引擎的命中/总长到底怎么算？——**这一条本轮翻过车**（见 §3），且证明必须用独立实现对账；
3. **判据**：本地生成接进产品既有 K2b 红线（`PromptCacheKpi`/`PromptCacheRedline`）时，分母该按谁的语义算。

## 3. ★ 本轮最重要的教训：口径必须靠独立实现对账，不能按字段名猜

**我一开始的（错）假设**: `tokens_evaluated` 是「本轮新评估数」（名字里就有 evaluated），命中部分在 `cache_n` 里 ⇒ 总长 = `tokens_evaluated + cache_n`。

**它导致的后果**（都在产品日志里看得见）: 热轮总长被虚增成 `530 + 512 = 1042`；`可复用上限` 随之膨胀到 1042；于是同一轮出现 **`有效命中率 = 1.0302 > 1`（物理不可能）**、下一轮又出现 **`0.523` 的假越线**。

**独立实现怎么把它钉死**: `/tokenize` 独立测出该渲染串只有 **529** token ⇒ `1042` 物理不可能；`tokens_evaluated(530) == prompt_n(18) + cache_n(512)` ⇒ **`tokens_evaluated` 就是总长**（含 BOS，比渲染串多 1）。

**可机检的特征**: 口径错时会出现 **>1 的比率**。这条已写进单测（`LlamaCppPromptAccountingTests.Trap_OldFormulaHalvesTheRatio`）—— 比率 >1 = 口径错，而不是「引擎好」。
（同理，按错误的换算，会话整体复用率会被腰斩到 0.4914，而真值是 0.9660 ⇒ 指标失真方向是**低估**。）

## 5. 设计决定（可被质疑的地方，写明理由）

1. **本地分母 ≠ 远端分母**（不共用 `PromptCacheKpi.CacheableTokens`）: 远端 provider 的「需要命中的部分」按 64-token 单元打折（mt_fix4 实测规律），而 llama.cpp 的 KV 缓存**连上一轮生成的 token 一起持有** ⇒ 套远端分母会把物理正常的复用判成「口径错」。两个 provider 的分母**各自独立**，禁止跨 provider 混算。
2. **判据 = 合取（复用率 ∧ 绝对长度）**: R410 已证「比值不是 KPI」。本轮负控正是这个情形 —— 复用率 99.81% 好看，但前缀只有 497 token，绝对省下的 token 是 0 量级 ⇒ 判越线。
3. **弃权与缺省**: 命中 > 可复用上限 ⇒ 记 `-1` 并计数 `Abstained`（不硬套判决）；命中未上报 ⇒ 视作全部重算、**不判红**（缺失 ≠ 错误）。
4. **`MaxTokens` 生效**（回复 23/34/29 字符）⇒ 每轮增量 ~17 token，这一点是「前缀占比」的关键自变量：**增量/总长 直接压低比值**。
