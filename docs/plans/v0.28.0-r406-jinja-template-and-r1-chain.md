# v0.28.0 · R406 模板驱动 chat template (Jinja 子集) 与 R1 链归因

状态: 已完成 (P0-2a 解释器 / P0-2b 生成路径接线)；进行中 (P0-1 llama.cpp oracle 收尾)

## 0. 一句话

把 chat template 从「只为 DeepSeek 手写的专用渲染器」升级为**从 GGUF 读 `tokenizer.chat_template` 原文 + Jinja 子集解释器**，
以 jinja2 3.1.6 渲染的三套金标夹具 (32 例) 做**逐字节**对账，并把生成路径切换到模型自带模板；
随后用「prompt 已证明正确」这一事实，把 R1-Distill-1.5B 的乱码输出**归因从模板侧移出**。

## 1. 因果链

1. R400 交付的 `ChatTemplate` 是**专用渲染器**（只为 DeepSeek 模板手写），对 R1 模板必然错；R405 实测差距：R1 9/10、qwen2.5-math 0/10，根因是 `ChatTemplate.cs:68` 无条件补 `<｜Assistant｜>`。
2. 但渲染器错 ⇒ **训练/推理/评测三处逐字节不一致 ⇒ 静默训出错分布**，所以必须先修链再谈权重改动。
3. 通用解不是「再手写一个 R1 渲染器」，而是**解释模板本身**（模板是 GGUF 自带的权威字节）。
4. 解释器要与 jinja2 对齐，必须先把**渲染环境选项用证据钉死**（不同 env 组合会产出不同字节）。
5. 环境钉死后，32 例夹具全过 ⇒ 渲染器不再是可疑项 ⇒ 用同一 prompt 跑自研引擎，乱码仍在 ⇒ **乱码根因不在模板**。

## 3. 判据（运行前预注册）

- **D1 env 反解**：对每套夹具枚举 `(trim_blocks, lstrip_blocks, keep_trailing_newline)` 共 8 组，取唯一能全过的组合。
  实测：qwen25-math 只有 `keep_trailing_newline=True ∧ trim_blocks=False` 才 10/10（`trim_blocks=True` 一律 0/10）；DeepSeek/R1 对 8 组**全不敏感**。
  ⇒ `JinjaOptions` 默认 `TrimBlocks=false, LStripBlocks=false, KeepTrailingNewline=true`。
- **D2 逐字节**：32 例 `rendered` 必须与 C# 输出**完全相等**（不是「长度相等」也不是「相似」）。
- **D3 长度单位显式**：每行必须有 `len_unit="utf8_bytes"` 且 `expected_len == len(UTF8(rendered))`。
- **D4 负控不可省**：模板互换必须**全不匹配**（证明对账对模板敏感，不是空心指标）；未实现构造/未闭块/未定义迭代必须抛。

## 5. 本轮发现并修复的缺陷

1. **夹具长度单位漂移**：`r1_chat_golden.jsonl` 的 `expected_len` 存的是 **Python 字符数**（10/10 行旧值==`len(text)`），另两套是 UTF-8 字节数 ⇒ 归一为字节 + 显式 `len_unit`；`chat_golden.jsonl`（deepseek）原本**没有**长度字段（其校验字段是 `rendered_sha256`）⇒ 本轮为它**新增**字段（不是修漂移，日志已自动更正）。
2. **夹具 env 标注与实际不符**：`chat_golden.jsonl` 标注 `env_options: trim_blocks=True,lstrip_blocks=True`，实测该模板对 8 组 env 全不敏感（标注不构成证据）；真正被 env 决定的是 qwen 套。
3. **llama-cli 会话模式无法关闭**：`-no-cnv` 与 `--no-conversation` 在本 build 均未生效（help 明示「有 chat template 时默认 auto 开启」），生成结束后 stdin EOF ⇒ 空转刷 `> `；4 MB 硬上限把事故限制在磁盘之外（1,397,341 行全为提示符）。证据归档 `eval/rover/r405/oracle-chat-mode-leak-trivial-2026-09-14.txt`。
4. **测试自身缺陷**：失败消息里用 `GetProperty("case")`（三套实际键名均为 `name`）⇒ 真失败时会抛 KeyNotFound 掩盖原因；已改 `name` 并补 `error`/`rendered_sha256` 校验。

## 6. 排除项（显式抛，不静默降级）

- `tool` 角色、多目标解包、`macro`/`block`/`call`/`filter`/`with`/`raw` 等成块关键字、未知过滤器/方法 ⇒ `JinjaUnsupportedException`（携带构造原文）。
- 未闭块、多余结束标签、未定义序列迭代、`str + none` ⇒ `JinjaEvaluationException`。
- `tojson` 等工具分支已实现但**未被夹具覆盖**（tool 分支为排除项），标注为「已实现未验证」。
- 无模板模型 `--chat` ⇒ 显式错误；`--chat-fallback-deepseek` 为**显式**开关（打印 `warn{...}`）。

## 7. 环境限制与诚实边界

- llama-cli 裸补全臂在本 build **不可得**（会话模式无法关闭）⇒ oracle 以 chat 臂为主，裸补全臂只作参照。
- 本轮 R1 生成 `ms_per_token≈3900`（≈3.9 s/token）是在 oracle 抢 CPU 时测得，**不可与既有 2.18 s/token 比较**；同轮 prefill 17 token 用 35.7 s。
- 32 例夹具来自**存档模板 + jinja2**，不依赖模型文件（模型已删/可换）；模板字节本身以 sha256 登记。

## 8. 待确认

1. **引擎 qwen2 前向正确性**（R1 乱码）：模板已排除 ⇒ 下一层嫌疑为 GQA(12/2) + `attn_q/k/v.bias` + untied `output.weight` 的组合路径、Q4_K_M 反量化、或该 prompt 的 OOD。
2. P0-1 oracle 收尾：llama.cpp **同一 prompt** 的 chat 输出（数学臂）——若 llama.cpp 能答 `144` 而我们不能 ⇒ 引擎缺陷坐实；若同样答不出 ⇒ 模型/量化边界。
3. 引擎速度（0.257–0.458 tok/s）与 llama.cpp（14.8 tok/s）差 32–57×，是否纳入下一轮性能靶点（P1 提速）。
