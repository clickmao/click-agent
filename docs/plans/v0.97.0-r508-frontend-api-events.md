## 4 改造方案（4 个发点，全部增量、可回滚）

新增事件（沿用既有 v1 信封，`FrontendApiContract.FormatEvent`）:

1. `task.started` — `{task_id, turn_id, started_at_ms, model, cwd, context_window, approval_policy}`
   发点: `FrontendApiChatRouter.cs:36` `ProcessAsync` 之前（`chat.send` 入口）。
2. `task.progress` — `{task_id, phase:"exploring|executing|thinking|waiting_user|cancelling", step_index, current_action, elapsed_ms}`
   发点: 动作环每次迭代边界（`ActionLoop` 节点回调 / `ILocalPromptRenderer` 渲染前）。
3. `item.started|item.updated|item.completed` — `{task_id, item_id, kind:"command|file_write|reasoning|message|plan", title, detail, output_tail, lines_total, truncated, exit_code, elapsed_ms}`
   发点: 工具调用前后；`detail` 由既有 `LogRouter` chatbox 通道升级为带正文。
4. `task.completed|task.failed` — `{task_id, status, reply, usage{input,output,cached,total}, elapsed_ms, exit_reason}`
   发点: `ProcessAsync` 返回后（替换/并列于 `chat.send` 的阻塞返回）。
5. `approval.requested|approval.responded` — `{task_id, item_id, command, reason, environment, options[{id,label,hotkey}], default_option}`
   发点: `FrontendPromptService.RequestOperationApprovalAsync`（P2 语义改写：**发事件 + 等待答复**，超时仍 fail-closed 拒绝，不伪造批准）。
6. `state.snapshot` 增 `tasks[]` — 运行中/暂停/等待用户的任务（phase、started_at_ms、elapsed_ms、current_action、last_item）。
   用途: 前端断线重连可直接恢复面板（对标 codex `codex resume`）。

兼容: `chat.send` 保持现有同步返回（老前端不破）；新前端订阅事件拿过程面。零反射要求 ⇒ 全部手写 `Utf8JsonWriter`（同 `FrontendApiChatRouter.cs:43-50` 既有做法）。

## 5 验收（可执行、机械判分）

| 编号 | 断言 | 判据 |
|---|---|---|
| A1 | 长任务事件序列单调有序、无缺口 | 事件流 `task.started → item.* → task.completed` 之外不出现；`step_index` 连续 |
| A2 | 事件与最终结论一致 | `task.completed.reply` == `chat.send.reply`（逐字节） |
| A3 | 等待用户不静默 | 审批场景必须出现 `approval.requested`，且任务 phase=`waiting_user`；超时才 `task.failed(reason=approval_timeout)` |
| A4 | 断线重连 | 重连 `state.snapshot` 的 `tasks[]` 与断线前最后 `task.progress` 对齐（task_id/step_index） |
| A5 | 老前端不破 | 无事件订阅时 `chat.send` 返回与改造前逐字节一致 |

## 6 排除项

- 不做前端渲染实现（本仓只出接口与事件）。
- 不做 MCP（既定立场）。
- 不改 `ask` 域语义（凭据问询保持 `ask/ask_closed`）。
- 不动 agent 内核决策链（只在既有边界挂发点）。
