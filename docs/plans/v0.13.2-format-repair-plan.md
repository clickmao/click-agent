# v0.13.2 增强计划: 格式修复收敛环插件 + 全局失败升级 skill

> 状态: 设计中 (用户钦定 2026-09-08, 文档先行)。
> 用户定义 (逐字要点): 格式修复需将修复代码写入 ```对应格式(如 json)代码块内;
> 做成 skill 放基础 skills 目录; 用户问询格式修复时先查是否存在对应格式技能,
> 无则走通用格式修复技能; LLM 返回后**不能完全相信**:
> ①查 LLM 是否把修复结果放进 ```json ...``` 内
> ②没放则运行独立脚本/程序查找
> ③找到合法字符范围 → 交脚本/程序校验是否正确
> ④不正确 → 脚本/程序本地修复
> ⑤无法修复 → 交回 LLM 修复后重新执行① — 循环直到通过。
> 格式化修复能力做成**插件服务** (能力增强计划), 提供基础 json/csv/xml 等常用格式。
> 需要多个用例和负样本校验基础修复插件正确合法。
> **技能-校验矩阵规则** (用户钦定):
> - 找到该技能但**没有校验机制** → **不进入循环修复步骤①** (不执行修复操作);
> - 存在校验能力但**没有本地校验程序** → 进入①且后续步骤全部由 LLM 尝试修复;
> - config: LLM 连续修复失败 N 次 (可计数, 因有校验机制) → 退出并向用户提醒任务存在问题;
>   若权限为全部托管给 agent → 可自行更改该步骤方案 (继续尝试本地修复/换方法)。
> **全局 skill** (用户钦定): 很多本地互动校验方案可分"用户确认 / 静默 agent 尝试查找数据依据寻找新方案新方法"两类;
> 该行为作为一个特殊全局 skill, 在**任意任务连续失败时自动插入**; 需要具体设计文档并声明在开发规范内, 后续开发遵照实现。

## 一、格式修复收敛环 (FormatRepairLoop)
### 1.1 流水线 (用户钦定 ①→⑤)
```
LLM 返回 → ①块内检测 (```json fenced block?)
  ├─ 有 → ③程序校验 (json.loads / xml parse / csv 结构)
  │        ├─ 过 → PASS (打点 repair_pass, source=fenced)
  │        └─ 不过 → ④本地修复 (确定性规则) → ③再校验
  │                  ├─ 过 → PASS (source=local_fix)
  │                  └─ 不过 → ⑤交回 LLM (带具体错误) → ①
  ├─ 无块 → ②独立查找程序 (从全文提取最合法候选区段 — 括号配平/引号扫描/格式头识别)
  │        ├─ 找到合法范围 → ③校验 → (同上分支)
  │        └─ 找不到 → ⑤交回 LLM → ①
  └─ 循环上限: config repair.max_llm_rounds (默认 3) → 超限 → 退出+提醒用户
```
### 1.2 本地修复器 (确定性规则, 插件化 IFormatRepairPlugin)
| 插件 | 格式 | 规则族 (可测试) |
|---|---|---|
| JsonRepairPlugin | json | undefined/null 归一; 尾逗号; 括号配平 (补/删); 缺值补空 {}; 单引号→双引号; 键名补引号; True/False/None→true/false/null |
| CsvRepairPlugin | csv | 列数对齐 (补空列); 引号闭合; 分隔符嗅探 (; , \t); BOM 剥离; 空行清理 |
| XmlRepairPlugin | xml | 标签闭合 (栈配平); 实体转义 (& < >); 声明头补全; 自闭合规范 |
| GenericRepairPlugin | 任意 | 降级: 仅做 ②查找+③校验, 无本地修复规则 (对应"无校验程序"语义的镜像) |
- 插件接口: `IFormatRepairPlugin { Format, CanDetect(text), FindCandidate(text)→(start,len)?, Validate(text)→errors[], Repair(text)→(fixed, changed_n) }` — 注册表模式 (与 ImageRenderPlugin 同构)。
### 1.3 技能-校验矩阵 (用户钦定, 硬性)
| 技能存在? | 校验机制? | 本地校验程序? | 行为 |
|---|---|---|---|
| ✓ | ✓ | ✓ | 完整收敛环 ①→⑤ 循环 |
| ✓ | ✓ | ✗ | 进入①, 后续全部由 LLM 修复 (无④本地修复) |
| ✓ | ✗ | — | **不进入循环修复** (不执行修复操作, 仅直答) |
| ✗ | — | — | 走通用格式修复技能 (GenericRepairPlugin 降级) |

## 二、skill 落位 (基础 skills 目录)
- `skills/format-repair/` — 主技能 (SKILL.md: 触发条件=用户问询格式修复; 格式分派表 json/csv/xml/通用; 矩阵规则声明; 循环语义)。
- `skills/format-repair-json/` (csv/xml 同构) — 专用技能, 存在则优先于通用。

## 三、config (用户钦定)
```yaml
format_repair:
  enabled: true
  max_llm_rounds: 3          # LLM 连续修复失败上限 (有校验机制所以可计数)
  on_exhaust: notify_user    # notify_user | agent_autonomous (托管权限 → 允许改方案)
  plugins: [json, csv, xml]  # 启用的修复插件
```
- 托管分支 (agent_autonomous): 超限后不退出, 改为"静默探索新方案" (见 §四), 打点 `repair_escalate (mode=autonomous)`。

## 四、全局 skill: 连续失败升级 (FailureEscalation — 用户钦定特殊全局 skill)
### 4.1 语义
任意任务 (批测用例/skill 执行/收敛环) 连续失败 ≥N 次 → 自动插入升级动作:
- **用户模式** (默认): 停止并向用户呈现 "问题 + 已尝试方案 + 失败原因 + 建议选项 (确认/换方案/放弃)"。
- **托管模式** (权限全托管): 静默 agent 自行查找数据依据 (RAG think-memory/历史轮 JSON/打点) 寻找新方案新方法, 继续尝试, 每次尝试打点。
### 4.2 声明位置 (用户钦定: 写进开发规范)
- 开发规范 (doc-driven-iteration-loop skill) 新增 "FailureEscalation 段": 后续一切带循环/重试的功能必须声明失败升级语义 (用户确认 vs 静默自主), 不得静默死循环。
- 打点: `task_escalate` (scope, fail_n, mode, actions[])。
### 4.3 与 v0.13.1 关系
- format-repair 的 on_exhaust 即 FailureEscalation 的第一个实例; sticky-route 的负样本记录为其数据依据来源之一。

## 五、样本集 (用例+负样本 — 用户钦定"多个用例和负样本校验插件正确合法")
### 5.1 正常样本 (FR-N01..)
| id | 输入 | 期望 |
|---|---|---|
| FR-N01 | 用户提供的破损 JSON (本任务实例: undefined/nested 空/尾多余}) | 修复=```json {\"cmd\":\"exec\",\"args\":[null,null,{\"nested\":{}}]}```; 校验过 |

| id | 诱饵 | 期望 |

| FR-F03 | 不可修复 (截断二进制/空串) | max_llm_rounds 耗尽 → 退出+提醒; 不死循环 |

| FR-F07 | csv 嗅探错误 (逗号实为数据) | 嗅探保守 → 校验不过 → 不强修, 升级 |

## 六、里程碑
- G1: IFormatRepairPlugin + JsonRepairPlugin (规则族+单测 ≥10, 含本任务实例回放)。
- G2: Csv/Xml 插件 + Generic 降级 + 注册表/技能分派 + 矩阵规则单测。
- G3: FormatRepairLoop 集成 (LLM 交互面 + config + FailureEscalation 全局 skill) + skills/ 落位。
- G4: 样本集跑测 (FR-N/FR-F 全绿) + 打点数据 + 有效性报告。

## 七、排除项
- 不做二进制格式 (图片/office) 修复 — 只做文本格式。
- 不在本地修复器里跑 LLM (LLM 只在⑤环入口)。
- 校验器必须用平台原生 parser (System.Text.Json / XmlReader / csv 结构规则), 不自造解析器当"权威"。
