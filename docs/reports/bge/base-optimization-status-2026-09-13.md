## 4. 本轮真发现（都在代码/文档层，非模型层）

1. **文档 ↔ 代码 G3 口径分叉（真 bug）**：`docs/plans/v0.22.0-exp7-…` §5 写 G3 = "每块延迟增幅 ≤15% ∧ RSS 增幅 ≤15%"；代码 `train_adapter.py:177` 实为 `g["G3"] = (mac/(24M×2)) ≤ 0.05`（算力占比 <5%），报告模板 `:252` 跟的是代码。→ 文档阈值与判定实现不是同一件事。
2. **G5 是空心闸门（真缺陷）**：`train_adapter.py:179` `g["G5"] = True  # 确定性: …由 --dry-run 重跑复核`。即**"确定性"这条闸门从未被自动执行**；台账"未过"列表不含 G5 只因它恒真。按用户审计标准（"没测到 ≠ 测过通过"），这属于判定空心。
3. **闸门粒度贴着噪声地板**：G2 阈值 = 0.83pt = **恰好 1 条查询**；而词法基线的同分 tie-break 口径（同分按文档索引升/降序）单独就能让 r@1 从 0.4417 变 0.4500（我已用独立实现复现两种取值：仓库口径 = 0.4417/0.7500/0.5571，与台账逐位一致 ✓）。→ 1 条级的判定不该当硬判决。
4. **闭环节奏正常**（非故障）：cron 15 次触发；最近两次产出为 `skip: load=2.26`（闲时门槛 loadavg<1.0，被我的编译/测试占用挡掉）；最后一次产版本 20:42:17（v9）。符合"闲时才跑"钦定。

## 5. 诚实边界

- T1 **不改底座权重**：它只能改表示空间，天花板受限；T2/T3 本机不可行（2 vCPU / 3.6 GiB）。
- 训练对 1004 条全部 **LLM 合成**（`llm-from-chunk`），不是真实用户检索标注；真实检索文本落盘仍未开启（exp7 §2.1 待裁定）。
- 词法基线是 1299 块小语料的**字符二元组 Jaccard**，不具跨语料外推性；它高于 dense 只说明"在这个项目源码语料上，字面重合是强信号"。
- `complementarity.py`（混合检索并集分析）**存在但从未跑出报告**——exp6 已下"混合检索才是正解"的架构结论，却一直没有实测数字背书。
- bge-m3 / qwen3-emb 在 exp6 里被成本淘汰（920MB / 1526MB RSS vs 2.2GB 可用），**评估表仍标"待补"**，未记录在案。
- R393 已交付 BGE 的 Vulkan 执行端口（真机 72/72、cos=1.0），但本机 GPU 是 llvmpipe 软件实现 ⇒ **比 CPU 慢（≈588–693ms vs ≈249–259ms/嵌入）**，不构成选型理由。
