## 0. 用户原话与拆解

### 0.1 原话（逐字保留）

> 「逻辑校验，修改当前步 看下上一步修改规则对齐当前 比如 让每个数字差别16间隔输出10个，之前输出到第8个，现在输出第九个的时候结束了看下第八个是否符合间隔16，（先查找所有修改位置 统一当作第九次，分开校验 诸如此类只是举例，再逻辑校验时可能产生问题给用户」

### 0.2 拆成四个可验收子能力

| 编号 | 子能力 | 用户举例对应物 |
|---|---|---|
| C1 | **修改位置查找**：对本轮产出定位所有"被修改/被追加"的位置 | "先查找所有修改位置" |
| C2 | **上一步规则提取**：从上一步的产物里抽出可机检**规则**（周期/步长/计数/格式） | "上一步修改规则"（差别 16 间隔） |
| C3 | **对齐校验**：当前步产物按 C2 规则逐点校验；边界点（末位）也要查 | 第 8 个是否符合间隔 16 |
| C4 | **校验失败 → 用户**：校验不过时把问题呈现给用户（不是静默跳过） | "再逻辑校验时可能产生问题给用户" |

> 注意 0.2 中 "统一当作第九次，分开校验" 的语义：**序号统一（本轮就是第 9 次动作）**，但**校验粒度分开（每个修改位置各自与规则比对）**——这是一个"归并口径 + 独立断言"的双层要求，直接影响 C1/C3 的数据模型。

## 2. 用户举例的可机检拆解（这是设计的关键）

用户例子："让每个数字差别 16 间隔输出 10 个；之前输出到第 8 个，现在输出第 9 个时结束了；看下第 8 个是否符合间隔 16"。

| 要素 | 机检化后 | 现有支撑 |
|---|---|---|
| "每个数字差别 16" | 序列约束：`a[i] - a[i-1] == 16`（容许 ±0 严格 / ±ε 可选） | **无** |
| "输出 10 个" | 计数约束：`len(seq) == 10` | **无**（`AcceptanceCriteria` 有字段但 0 消费方） |
| "之前输出到第 8 个" | 上一步产物状态：最后一项值 + 序号 | **无**（产物不持久化，§1.3） |
| "现在第 9 个时结束了" | 本轮修改位置：第 9 项（新增）+ 末端边界 | **无**（无修改位置查找，C1 缺失） |
| "看第 8 个是否符合间隔 16" | 边界点校验：末位之前的相邻差检查 | **无** |

**结论**：用户举例的每一步在当前代码里都没有对应实现；这不是"接线"问题，而是**缺一层约束模型 + 一层产物留痕**。

## 3. 与 `CorrectionDetector` / `FailureClusters` 的职责边界（避免重复造轮子）

| 维度 | `CorrectionDetector` | `FailureClusters` | 本探索项 C1–C4 |
|---|---|---|---|
| 判定对象 | 用户的**回答**是否纠正了 agent | 会话是否**空转/中止** | **产物**是否符合**上一步规则** |
| 输入 | 上一轮 agent 提问 + 用户回复 | 近 3 轮回复相似度 | 上一步产物 + 本轮修改位置 + 约束 |
| 时序 | 轮后 | 轮后 | **生成前/生成后**均可 |
| 输出 | 赏罚信号 → GrowthLedger | 罚分 → 前置警告 | 校验结论 → 用户/修复环 |
| 可否替代 | 否 | 否 | — |

**边界铁律**：C3 的结论必须是**机器可判**的（数值/计数/正则），不得由 LLM 自证"我符合规则" —— 否则就是用户定性过的"判定空心"。

## 4. 推荐设计（探索结论）

### 4.1 数据模型（新建，最小可用）

```
TaskConstraint {           // 从用户指令抽取，落 GoalProfile 旁挂
  Kind: Counting | StepDelta | Period | Format | MustContain
  ParamsJson: {"start":?, "delta":16, "count":10}   // 结构化, 不靠自然语言
  Source: 原文片段（≤60 字, 审计用）
  Strict: bool
}
StepArtifact {             // 每次修改后的产物留痕
  StepIndex: int           // "统一当作第九次" → 全局序号
  Sites: [{Path, Start, End, Kind}]   // C1 修改位置（本轮所有改动点）
  Payload: string | JSON   // 受限长度（尾部 N 项 + 头尾指纹，避免全量落盘）
  AtUnixMs
}
```
- 关键：`Sites` 是**多个**（"分开校验"），`StepIndex` 是**统一**的（"统一当作第九次"）——这正是用户 0.2 的双层要求。
- 归并键复用现成 `ClusterKey` 的 FNV-1a 稳定指纹 `[src/agent.roles/FailureClusters.cs:77-107]`（跨进程稳定，R365 已修），不新造。

### 4.2 校验器（机器侧，无 LLM）

`ConstraintEvaluator.Evaluate(constraint, stepArtifact, prevArtifact) → Verdict{Pass|Fail|Inconclusive, Evidence[]}`
- `StepDelta`：逐点 `a[i]-a[i-1]`，输出**违例下标**；`Inconclusive` 仅当产物非结构化且无法解析（诚实标注，不伪装 Pass）。
- 边界规则：末尾新增点时，**必须回查前一个点**（用户例子第 8 个）——实现为"校验窗口 = 新增点 ∪ 其前驱"。

### 4.3 接线点（最省改动）

1. 生成后：V2 主链在产出定稿处调用 `ConstraintEvaluator`（参照 `GuardrailMemory` 注入点的位置 `[src/agent/IndustrialAgentV2.cs:1984-1993]`）。
2. 失败：`Fail` → ① telemetry `constraint_violation`（复用 `AgentTelemetry.Emit`）② 复用 `IUserPromptService.RequestOperationApprovalAsync`/问询通道上报用户（C4）③ 可选接未接线的 `FormatRepairLoop` 做一次收敛修复。
3. 前置：把 `StepArtifact` 摘要注入 prompt（防止"忘了第 8 个是什么"）。

### 4.4 与"长任务断链"的关系（用户 OOB 关注的同一条线）

产物不持久化（§1.3）是长任务断链的**根因之一**：跨步无记忆 → 后续步只能靠上下文猜上一步做了什么。本项的 `StepArtifact` 同时是长任务的"续跑锚点"，一举两用。

## 5. 关键约束

1. **零反射 / NativeAOT**：新模型一律手写 `Utf8JsonWriter`/STJ 源生成；禁 `JsonSerializer.Deserialize<T>` 反射路径。
2. **机器可判优先**：LLM 只许参与"从自然语言抽约束"，**不许**参与"校验结论"。
3. **诚实边界**：无法机检时必须返回 `Inconclusive` 并上报，不许静默 Pass（负样本诚实铁律）。
4. **零 shell**：若校验需跑外部命令（如 `python -c` 验算），一律 `ProcessStartInfo.ArgumentList`。
5. **产物留痕隐私**：`Payload` 只留尾部 N 项 + 指纹，防上下文/磁盘膨胀。

## 6. 验收标准

| # | 断言 |
|---|---|
| A1 | 给定用户例子（间隔 16、共 10 个），构造第 8 项违约的产物 → `Evaluate` 返回 `Fail` 且 `Evidence` 含违例下标 7→8 |
| A2 | 第 9 项新增时，校验窗口包含第 8 个点（边界回查），单测锁死 |
| A3 | 同一次修改有 3 个位置 → 产出 3 条独立 Evidence，且 `StepIndex` 为同一序号（"统一当作第九次，分开校验"） |
| A4 | 校验失败产生用户可见上报（telemetry 点 + 问询通道各一条），有单测/端到端证据 |
| A5 | 无法解析的产物 → `Inconclusive`，**不**计 Pass（负样本诚实） |
| A6 | 全量测试绿 + AOT 0 IL 警告 + 二进制体积不劣化 >5% |

## 7. 排除项

- 不做通用定理证明/符号求解器（超出需求）。
- 不引入 Python/外部求解器作为校验依赖（校验必须纯托管）。
- 不替代用户判断：校验只给"违例证据"，最终是否接受由用户/上层策略定。
- 不重构 `CorrectionDetector`/`FailureClusters` 语义（边界见 §3）。
