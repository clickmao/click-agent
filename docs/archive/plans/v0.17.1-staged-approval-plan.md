# v0.17.1 离线变更与用户审批计划 (R335 立项 — 用户钦定 2026-09-10)

> 用户指令 (逐字核心): "增加离线 变更 用户审批计划，CLI产出内容部分需要用户审批，比如在做文件修改时产出了一堆文件但是需要用户审批变更（比如vs code用户正在编辑同代码文件时不能直接覆盖用户正在编辑的文件），但CLI不能停，而文件变更不能长久停留在内存内，需要落盘却不能占用真实文件地址，且用户下次打开CLI时文件未审批但变更已存在如何恢复，变更存在过期周期如何设计？ 前端如何取得变更信息，批次和实际落盘变更文件内容，多批次变更如何合并等问题"

## 0. 现状与差距

- 现写路径 (Workspace.cs / file_operation / 各类 Save) 直接写真实文件 — 无审批闸门, 可能覆盖用户正在编辑器里改的文件。
- v0.17.0 (R334) 已有跨进程锁/原子写/占用者检测/教训记忆 — 审批应用层复用 LockedFileWriter.WriteIf (基线比对防覆盖) + ExecutorLessonMemory (冲突记教训)。
- 指令框架 (LocalCommandRouter + V2 特判渲染) 已有 /skills 族先例 — /staged 族同款接入。

## 1. 设计 (逐问题回答)

### Q1 CLI 产出需审批, 不能直接覆盖用户编辑中的文件 → **staging 区**
- 任何"文件修改产出" (一期: agent 主动产出; 后续: 全部 Workspace 写) 默认不写真实路径, 而是写入 staging 区 `data/staged/` (独立目录, **不占用真实文件地址** — VS Code 正在编辑的文件零感知)。
- 批次 = ChangeBatch: `{Id, CreatedUtc, TtlDays, Status(pending|approved|rejected|expired|partial), Source, Items[]}`。
- Item: `{Path(真实目标), BaselineSha256(批次创建时目标文件哈希 — 应用时比对), ContentFile(staging 内完整新内容), Applied(bool)}`。存完整快照非 diff — 合并/回滚/展示都简单 (git 式 index 的简化版)。

### Q2 CLI 不能停但变更不能久留内存 → **落盘即批**
- 产出完成 → 立即落盘 data/staged/<batch-id>/{content 文件们} + 原子写 index.json (LockedFileWriter) — 内存零滞留; CLI 继续下一任务。
- 未审批批次跨会话存活 (data/staged/index.json 持久) — 进程重启不丢。

### Q3 用户下次打开 CLI 未审批变更如何恢复 → **启动提示 + 指令查询**
- V2 boot/会话开始: 若 index.json 有 pending 批次 → 输出 "📋 N 个未审批变更批次 (上一会话产出) → /staged 查看, /approve <id|all> 应用, /reject <id> 丢弃"。
- `/staged` 列全部批次: id/时间/源/状态/文件数; `/diff <id>` 显示逐文件内容; `/approve <id>`; `/reject <id>`。

### Q4 过期周期设计 → **三阶段 (不静默删)**
- TTL 默认 7 天 (config `staging_ttl_days`): 到期 → Status=expired (文件保留, 可 /diff 查看仍能取回);
- TTL×2 → 标记 reclaimable; `/cleanup` 或 config `staging_auto_discard=true` 才物理删除。
- 原理: 审批是用户资产 — 宁可保留标记过期, 不静默丢 (与教训记忆同哲学)。

### Q5 前端如何取得变更信息/批次/内容 → **双通道**
- ① 状态文件: `data/staged/index.json` (前端/宿主直接读 — 结构化, 原子写, 含批次元数据+文件清单+完整内容路径)。
- ② 指令 JSON 输出: `/staged --json` → 单行 JSON 供宿主解析 (lightclaw/qq 前端)。
- 完整内容 = staging 内文件 (不占真实地址), 前端读 contentFile 即得实际落盘变更内容。

### Q6 多批次合并 → **按创建序应用 + 基线冲突拒绝**
- `/approve all` = 按 CreatedUtc 升序逐批 apply (用户 A/B 批都产出同文件 → B 批基线哈希含 A? 不 — 基线哈希在创建时定, 若 A 未应用 B 先建 → B 基线=原始文件; 应用 A → 文件变 → 应用 B 时基线不匹配 → **conflict**, 该项拒绝 (不覆盖), 批次记 partial, 报告冲突文件要求用户 /diff 后手动合并或 /reject B 重跑)。
- apply 用 LockedFileWriter.WriteIf: 锁内比对当前文件 sha256 == Item.BaselineSha → 等则原子写 (用户未动过 → 安全), 不等 → conflict 拒绝 (用户正编辑/已改 → 绝不覆盖) — **Q1 VS Code 场景的机械保证**。
- 冲突教训入 ExecutorLessonMemory (pattern "staging-conflict:<path>" 频率加权 → 提示用户先 /approve 早期批或避免并发产出同文件)。

## 2. 模块 (src/agent/staging/)

- `StagedFileStore.cs`: 批次 CRUD + 持久化 (index.json 经 LockedFileWriter 原子写) + 过期扫描 + 恢复加载。
- `ChangeBatch.cs` / `StagedItem.cs`: 模型 (手写 JSON 或 STJ source-gen — 同 TaskCharter 模式)。
- `ApprovalController.cs`: Apply (WriteIf 基线比对) / Reject / Diff 渲染 / Expire 扫描; 返回结构化结果 (approved/conflict/skipped 明细)。
- `StagingSha.cs`: sha256 工具 (BCL IncrementalHash — AOT 安全)。

## 3. 指令接入 (LocalCommandRouter + V2 特判, /skills 族同款)

- `/staged [--json]` → 列批次; `/staged diff <id>` → 逐文件内容; `/approve <id|all> [--force]`; `/reject <id>`; `/cleanup`。
- V2 boot 提示 pending 批次 (恢复入口 Q3)。

## 4. 写路径接入 (一期)

- 新增产出默认进 staging: file_operation skill 的写操作 + `agenthost --stage-writes` 时全部 Workspace 写转 staging (config 开关)。
- 默认关 (不破坏现有 37 案批测); E2E 用开关验证。

## 5. 验收标准

1. 单测: 批次创建落盘 (内容在 staging 不在真实路径) / 恢复加载 (新实例读 index.json) / 过期三阶段 / apply 成功 (基线匹配→真实文件写入, staging 清) / apply conflict (用户改过→拒绝+partial) / approve all 顺序合并 / reject 丢弃 / --json 输出 / 原子写损坏容忍。
2. E2E: `--stage-writes` 起 host → 触发产出 → 真实文件未变 + /staged 可见 → 编辑目标文件 (模拟 VS Code) → /approve → 冲突拒绝不覆盖 → 恢复原状 → /approve 成功。
3. 全量单测 581+ 绿 + AOT publish 0 IL 警告 + quick-13 零回归。

## 6. 排除项

- 不做自动 3-way merge (冲突即拒绝, 报告人工); 不做图形 diff UI; 不改 RAG/记忆等内部数据写路径 (非"用户文件产出"); 增量 patch 格式 (完整快照足够且更稳)。
