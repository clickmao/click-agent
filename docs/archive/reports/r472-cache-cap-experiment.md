# R472 报告 —— 远端前缀缓存「饱和」成因判定(真机受控实验): 不是供应商上限

**外部真值**: `https://api.deepseek.com/v1/chat/completions`, 模型 `deepseek-flash`(≡ `config/base/models.yaml:9,16` 生产配置), 8 次真机调用, 请求体 max_tokens=16 / stream=false, 逐调用原始 `usage` 落盘 `eval/rover/r472/real-usage-r472.jsonl`。

## 2. 结论: NO_CAP(不存在 ~2.1k 硬上限)

1. **数据级直接证伪**(不依赖任何判定函数): 观察到 `hit = 5,632 > 2,304`(R469/R470/R471 假设的饱和上沿) ⇒ 「缓存命中在 ~2.1k 处被 provider 截断」为**假**。
2. **命中随共享前缀线性增长**: 前缀 910→3,789→5,811 tok 时命中 768→3,584→5,632, 比值 0.844/0.946/0.969 单调升(趋 1) — 若存在 2k 上限, 后两臂应并列在 2,048 附近。
3. **机制定律**(事后派生, 5/5 点吻合): `prompt_cache_hit_tokens == 64 × ⌊(prompt_tokens − c) / 64⌋`, **c = 142 唯一解**(5 点不等式交集 [142,142])。即: 命中量只由「与历史调用共享的前缀长度」决定, 精确到 **64 token 块**; 全部 5 条 warm/复现调用命中均为 64 的整数倍(12/56/88 块), 而 prompt 长度不是。
4. **负控**: 三条 cold(唯一 nonce 开头, 与任何既有文本无共享前缀)命中 **0/0/0** ⇒ 上表命中确实来自「本实验共享前缀」, 不是环境里的偶然缓存。

## 3. 对主线的后果(R469/R470/R471 口径必须修正)

真实流 43 条 `llm_call`(prompt 229–6,360, 中位 3,064; hit 0–2,304: 19×2,048 / 7×2,176 / 2×2,304 / 2×256 / 2×127 / 11×0; R470 已证 43/43 **无同会话前驱**):

| 旧口径(假设硬上限) | 新口径(实验支持) |
|---|---|
| 命中率上限 ≈ 2.1k, 与 prompt 无关 ⇒ 长轮 97% 红线「结构性不可达」 | 命中 = 可复用前缀(块对齐) ⇒ 红线不可达的原因是**该样本每条都是无前驱首调 + 4k 私有任务文本**, 不是 provider 能力上限 |
| 升稳定前缀 >2.3k 无收益 | 升前缀**有效**, 但只在它把「本来要新算的内容」变成「跨调用复用内容」时才有效 |
| `shared_prefix` 通道 = 跨会话复用(定义在饱和值上) | 通道定义不变, 但基线 miss 59,518 的成因解释改为「2.1k 脚手架 + 1.0–3.5k 各会话私有文本」 |

⇒ 「97% 不可达」的**机制表述**被证伪(采样面=无前驱首调所致), 而非「红线本身达不到」; 对多轮会话, 命中量 ≈ 前一轮 prompt 长度 ⇒ 命中率随轮次单调上升。

## 4. 诚实边界

- **本轮无 C# 改动** ⇒ 按铁律**不触发** AOT 重发布(是「不触发」, 不是「未测到」); 体积沿用 R470 `agenthost` 15,343,232 B。
- **预注册判据 C7(判定函数自检)判 FAIL**: v1 的 CAP 分支阈值(`r_MID ≤ 0.65`)与前缀臂尺寸不自洽(需 `P_MID ≥ 3,150` 才可达, 合成 case `cap=2048/P_MID=2600` 因此判成 PARTIAL)。按判据纪律: **原判保留 FAIL 不覆盖**, 修正单列 post-hoc(`posthoc-r472.json` P1/P3), 修正版 v2 自检 4/4 通过, 且真实数据在 v1/v2 下**同判 NO_CAP** ⇒ 结论不依赖判据修正。
- **外推有界**: 合成 filler 而非产品提示词 ⇒ 本轮证明的是 **provider 机制**, 不是产品链的真实命中; 产品链命中仍只有 R470/R471 的**派生值**(实发样本 0, R471 已记录)。
- 未测: 命中/未命中的**计价差**(只测 token 计数); 其它 provider/模型; 真实流 43 条「脚手架 ≈ 2.1k」是**推断**非直接测量(需实发 prompt 文本, 当前 0 样本)。
- `c = 142` 的内部构成(聊天模板 vs 用户消息)未逐 token 拆解 ⇒ 标「待确认」。

## 5. 下轮候选

1. **真机多轮会话实测**(同会话 ≥5 轮): 验「hit_{n} ≈ prompt_{n-1}」与「每轮新算占比」⇒ 直接给出用户 KPI(一轮任务 token)的分母分解, 并把 97% 红线重述为「首调 vs 多轮」分档判据。
2. **产品链实发样本**(R471 ③, 仍 0 样本): 有了机制定律后, 可预注册形式断言 `hit == 64×⌊(可复用前缀−c)/64⌋` 锁住产品接线。
3. **私有增量压缩 A/B**(按需注入): 同任务两臂对比 miss tokens —— 现在方向明确: 唯一杠杆是把「新算」变成「复用」。
