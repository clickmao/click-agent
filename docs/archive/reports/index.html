如何利用形式化验证增强 Agent 自身的逻辑能力
——形成逻辑思维闭环、提升体验并节省 token

本报告回答一个问题：把「形式化验证」从数学定理证明的专用工具，移植为 agent 运行时的逻辑裁判，是否可行、以什么形态落地、能省多少 token、以及在哪里会失败。结论基于 12 组公开文献的多方对账，并与本项目已有基线（本地 Prover 引擎 click-rover、缓存命中率口径、契约前置注入）对齐。

结论：可行，条件性 三条落地路线 12 组文献证据 6 类形式化用例 5 项可测验收判据

00结论速览

先给裁决，再给依据。以下每条都可被下文的文献数据或本项目基线数据反驳。

裁决 1

「逻辑闭环」成立，但闭环的位置不是模型，是运行时

文献一致指向同一结论：LLM 负责提议（生成候选证明/候选计划），验证器负责裁判（不可协商的通过/拒绝）。把二者放进同一个自回归循环里让模型"自我批判"，收益远低于让外部内核做硬判定。最强证据：编译器反馈单独一项就把忠实形式化率从 19.75–36.00% 抬到 58.75–62.00%（+32.3 点）。

裁决 2

token 节省是真实且可归因的，但有前置条件

节省不来自"少说话"，来自四件事：本地验证零 token、契约前置消灭澄清轮、已验证结论缓存复用、错误分支早停。文献侧对应证据：符号检索使昂贵编译-修复循环调用次数下降 26.6–29.8%；奖励引导解码最高减少 4.4 倍 FLOPs。前提是验证判定必须是确定性的，否则省下的 token 会以重试的形式还回去。

裁决 3

最大风险不是验证不通过，是「验证通过了但意思错了」

这是本报告最重要的一条。形式化只保证"模型写下的命题被证明"，不保证"这个命题是你想说的那个"。实测：编译通过率 89.5%，语义忠实率仅 60.5%，缺口 29.0 个百分点；跨 8 个系统的缺口范围 3.0–29.0 点。任何把"编译通过"当作正确性证据的设计都会系统性放大这个缺口。

裁决 4

推荐形态：五层增强（契约 / 本地内核 / 证据缓存 / 闭环 / 信任台账）

不自研定理证明器，不替换现有 LLM 链路。在最外层加"可验证契约"，在最内层加"本地、零 token、可离线重放的验证内核"，中间用证据缓存把重复推理变成查表。工程可行性已被外部实现证明量级：约 1900 行核心代码 + 130 个测试即可覆盖污点分析、安全自动机、Z3 定理证明三类静态检查，且验证阶段不需要任何 LLM 调用。

一句话方案

让 LLM 的每一次关键输出都附带一段机器可判定的形式化断言（claim + formal + witness + 证据等级）；本地验证内核用确定性规则（模式/约束/数据流/内核检查）在零 API token 下判定；通过则把结论与其证明一起冻结进证据缓存，失败则把反例或最小冲突核回注给规划器。验证通过的东西从此不再重复推理——这就是逻辑闭环与 token 节省的同一个机制。

01问题拆解与边界

先把问题本身定义清楚，否则"增强逻辑能力"是一句无法验收的话。

1.1 「增强 agent 自身逻辑能力」的三种口径

同一句话的三种可验收解释，只有第二种能被本轮方案覆盖。
口径含义可验收判据本轮覆盖
① 参数层增强用形式化数据继续预训练/微调模型本体，让参数里长出逻辑能力同题基准准确率提升，且不退化部分 仅本地 7B 蒸馏模型

1.3 边界与非目标

  • 不做模型微调替代方案：参数层增强与本方案正交，可叠加但不作为闭环前提。
  • 不做通用定理证明器：数学定理只是用例之一；本方案的内核是"确定性裁判 + 证据台账"。

#用例形式化对象验收判据（可机检）

04click-verify：五层增强架构

与现有链路正交：不改 LLM 主体，不引入本地 LLM 加载层；新增的只有契约、判定、缓存、闭环、台账五件事。

4.1 每一层做与不做的事

L0 契约层
做：把接口契约写成确定性断言并源生成进静态前缀。不做：契约的语义正确性自动判定（契约由人/审计定义）。
L1 本地内核
做：确定性判定 + 本地模型复核；输出"通过/拒绝/弃权"三态与证据。不做：任何网络调用；不做自然语言判别。
L2 证据缓存
做：以断言指纹为键冻结证明工件与引理；命中直接返回。不做：跨语义等价但字面不同的断言的自动合并（指纹只认结构）。
L3 闭环层
做：有界重试、最小冲突核回注、失败可见。不做：无限重试；不做静默降级（失败必须上报）。
L4 信任台账
做：等级栅格、不可上溯、经验沉淀为 skill。不做：让 LLM 自己给自己升级证据等级。
与现有系统的接缝（不新增破坏面）
  • 契约与后置断言挂在已有节点结果契约上（现有节点结果对象已含产出与状态，扩展为带断言集）。
  • 验证判定发生在执行前/执行后两个固定点位，不侵入规划器内部推理。
  • 失败回注走已有重试/续跑通道（检查点与等待机制已具备），不新建调度。
  • 证据等级作为输出元数据附带，前端可选择展示"此结论已被机器验证"以增强用户体验。

05形式化符号返回协议

闭环的入口是"LLM 返回时附带形式化符号"。协议设计决定后续一切：字段越少越好，且必须可判定、可拒绝、可弃权。

字段含义判定规则
claim用自然语言重述的结论（给人读，也给忠实性复核用）必须与 formal 成对出现；只有其中之一 ⇒ 拒绝
formal机器可判定的断言（约束式 / 前置后置 / 命题式 / 计划图）解析失败 ⇒ 直接拒绝，不回注猜测；不得静默降级为自然语言判定
witness支撑断言的可核查证据：具体取值、数据来源标识、证明项或冲突核缺 witness 的结论一律降为"合理"，不得进入已验真
grade模型自评的证据等级（仅作输入，不作结论）最终等级由 L4 按不可上溯规则重算；模型自评只能降不能升
scope断言适用的前提与边界（什么条件下成立）作用域外的调用视为未验证；防止结论被跨语境滥用

5.1 为什么必须允许「弃权」

外部证据给出的最重要工程教训之一是：不能证明时的正确行为是诚实弃权，而不是猜一个看起来合理的答案。四层信任台账框架把"弃权"做成了一等结果，并因此把潜在幻觉转化成了可审计的、可度量的形式化失败。对我们而言，弃权还带来一个直接收益：它把"再试一次（花 token）"与"承认不知道（零 token，交还用户）"分开，避免在无解路径上无限消耗预算。

反向约束（先写好失败条件）

任一条 KPI 相对基线恶化 ⇒ 立即关闭验证层并回退，不以"架构更先进"为由保留。这一条写在最前面，是为了防止验证层变成只增成本不减 token 的装饰。

四条机制各自独立、可单独开关、可单独度量。量级给的是保守区间与来源，不是承诺值。

最诚实的一句

token 节省的真正来源不是"验证器让模型变聪明了"，而是"已经验证过的东西不再重新推一遍"。这也是为什么缓存层（L2）在架构上比模型层（L1 的本地 7B）更关键：前者每天省钱，后者只在数学类用例上挣钱。

08风险与反证

按"如果我们错了，最先从哪里看出来"排序。每条风险配一个能在早期观测到的信号。

8.1 忠实性缺口：验证通过 ≠ 意思对了 最高风险

形式化只保证模型写下的命题被证明，不保证该命题等同于用户的意图。实测缺口：全工具 agent 编译通过 89.5%，语义共识忠实 60.5%，缺口 29.0 个百分点；另有跨 8 系统 3.0–29.0 点的缺口区间，人工审计确认 95/114 个"编译通过但被判不忠实"确属语义失败。

  • 早期信号：验证通过率高、但用户回读后要求修改的比例也高。
  • 缓解：① 断言必须成对回读（自然语言重述 + 形式化）；② 用多源交叉判定而非单一判据；③ 把"忠实性等级"与"验证结果"分开记录；④ 引入反事实探针（对外部证据中的注入做压力测试）。
  • 判据：反事实注入下溯源忠实率 ≥ 基线；用户"验证通过但结果不对"的上报数为零增长。

8.2 形式化博彩（formalization gaming）

当"验证通过"成为优化目标时，系统可能学会写更容易通过的形式化，而不是更正确的结论——与规范博弈同源。论文已记录模型可能利用评测缺口的行为。

  • 缓解：断言集由契约层定义（模型不得自选判据）；每日抽样人工复核；长轨迹设置告警。
  • 判据：抽查样本中"断言被改写得更容易通过"的事件数为零。

8.3 长轨迹反而更不忠实

观测：在启用编译器反馈的配置下，1–2 步轨迹的忠实率 81.3%，19–24 步时降到 12.0%。即"再多修几轮"是负收益区间。

  • 缓解：闭环重试上限≤1–2；步数超阈值时强制降级为弃权并交还用户。
  • 判据：重试次数分布右尾被截断；超长轨迹不再产生"已验真"等级。

8.4 本地 7B 裁判的能力上限

7B 蒸馏版在数学类基准上表现可观，但领域窄、且本机无 GPU（仅 CPU 实测路径），吞吐受限。

  • 缓解：本地模型只做"独立复核"与"缓存生成"，不做唯一真值来源；非数学类判定走确定性检查器。
  • 判据：本地复核与真值来源不一致时，记录为弃权而非通过。

8.5 验证覆盖 ≠ 正确性；成本 ≠ 零

被验证的部分可信，未被覆盖的部分一如既往。同时验证层本身要消耗本地算力与工程维护成本。

  • 缓解：输出中显式标注"已验证 / 未覆盖"，让用户看到边界；验证层可整体开关。
  • 判据：关闭开关后所有基线数字逐位复原。

8.6 现实上限

外部最强工程化实现给出的决策合规率为 90.5%，并非 100%。任何宣称"验证后绝对正确"的设计都不成立。

8.7 方法论教训：同源对账 = 自证（本次实现当场抓到） 已复现

本方案自研的本地推理引擎在解析 GGUF 时，把数据区起始偏移算在「KV 段之后」对齐；规范要求算在「张量信息段之后」对齐。本模型因此少算 16,192 字节（恰为 273 条张量信息的字节量），所有张量窗口整体前移，反量化出的权重全部错误——真机前向实测 y_sum = NaN。

为什么第一轮没抓到：初版用官方参考内核（ggml-quants.c 直链）对同一张量对账，得到 differing=0 / exact_match。但参考内核吃到的是同一份错误偏移下截出的字节——两边只是互相印证了同一个错误，验证通过 在这里不构成任何证据。换成第三方独立解析实现（python-gguf，纯 Python/NumPy）后，差异立刻在 16,192 字节处暴露。

  • 验证判据（可机检）：跨实现对账必须换独立解析实现——不同来源、不共享偏移推导代码；判据 = 三方（自研解析 / 参考内核 / 独立解析）在同一张量上 diff = 0，而非两方一致。
  • 修复后实测：data_offset = 3,990,784（与第三方一致）；5 张量 × 2 文件（4.2 GB 7B / 334 MB 检索模型）× Q4_K+Q6_K 全部 diff=0, max_abs=0；并行路径互查 max_abs_diff = 1.9e-06（fp32 精度内）。
教训抽象（语言无关）：当验证者与被验证者共享同一个前提推导时，「通过」不构成证据。任何验证链都必须至少包含一个不共享该推导的独立观测点——否则一致性只证明了两者在同一个错误上达成共识。

每阶段独立可验收、独立可回退。P0 不依赖任何新模型能力，因此在本地引擎完成前即可上线并先拿到 token 证据。

10待确认项

这些是会改变设计的选择题，需在实施前定稿；未定稿前不进入实施。

  1. 断言来源：契约由人工/审计定义，还是允许 LLM 生成候选断言再由人复核？后者扩张速度快但引入 8.2 的风险。
  2. 证据等级的展示策略：是否在用户可见输出中标注"已验证"？标注增强体验，但也可能诱导用户过度信任未覆盖部分。
  3. 数学类用例的优先级：本地 7B 裁判是否值得投入（受本机无 GPU 限制），还是先只做确定性检查器、把数学类留到算力就绪。
  4. 缓存指纹粒度：按断言结构、按语义哈希、还是按来源+作用域组合？粒度越粗越省钱、越细越安全。
  5. 弃权的用户体验：弃权时是直接告知未验证，还是给一个低等级的候选答案并明确标注？
  6. 与既有续跑机制的关系：验证失败是否复用已有检查点/续跑通道，还是走独立重试计数。
